# Eddie architecture: voice implementation status

The backend API and DNS enforcement are independent of the voice worker. Development currently uses the Mac microphone and a localhost dashboard; production should run the same offline worker on the final box after ARM64 performance checks.

Audio → openWakeWord custom ONNX → bounded in-memory capture → faster-whisper local model → deterministic tool router → local REST API → Piper → audio output.

The dashboard bridge publishes `voice_status`, `wake`, `voice_state`, `transcript`, `agent_reply`, `speaking`, and `speech_end` events through its existing SSE connection. It accepts start, stop and typed ask requests. Speech and typed responses share a serialized lock. Recognition discards input during replies and resets detector history before rearming.

Implemented tools are backend summary reads, “what they know” inference reads (`what_they_know` → `GET /what-they-know`) and home-mode writes. Inferences are deterministic facts from the event log (including sessions of one category with gaps under 10 minutes, and category by weekday). The router honors explicit ranges such as “the last 3 days” or “two weeks”; with no range it requests all locally retained history. The API caps longer requests to `EDDIE_RETENTION_DAYS`, discloses the cap, and returns `enough_data: false` rather than offering an inference with fewer than two observations. When the local model is on, `ollama_agent.phrase` writes at most five "Someone could guess …, because …" lines from the facts alone (no tools, one call, 20 s limit); lines with a number, clock time or weekday not in the facts are dropped, and the backend template is spoken if none survive or the model is down. On the development Mac with `llama3.2:3b` and the demo week this took 4 to 9 s, and each kept line quoted its evidence; the check cannot catch a misread fact. `GET /what-they-know?demo=true` runs the same code on a seeded, labelled demo week (`eddie/demo_week.py`); the dashboard shows it under a DEMO DATA banner and voice never reads it. Home mode is backend state, not evidence of DNS enforcement. Missing tools explicitly report that no change occurred. The model does not fabricate counts. Ollama tool calling (#29) sits on that boundary for read-only questions; see below. Lockdown (#17) and away mode (#109) use the confirmation state below; email will too.

## Local tool-calling agent (#29)

`voice/ollama_agent.py` runs a bounded Ollama `/api/chat` loop (temperature 0, at most 4 model calls and 30 s per question, 20 s per call) with the README system prompt and four read-only tools: `get_summary` (`GET /summary?window=` per-device counts, plus one factual sentence per device for the model to repeat), `get_recent_blocks` (`GET /events?action=block`), `explain_domain` (latest `/events?domain=` row and any `/ai/verdicts` entry) and `what_they_know`. Spoken device names are matched leniently ("the TV" matches a Fire Stick, Roku or Chromecast label); an unknown name returns the known devices to the model. Argument errors go back to the model; a backend failure ends the turn with a fixed "can't reach the backend" line. The reply is checked so every number in it appears in the turn's tool results; otherwise Eddie falls back to backend text or says it can't verify. If Ollama is down, slow or loops, `answer` returns `None` and the deterministic keyword router answers instead.

Write tools (#108): `block(domain)`, `allow(service | domain)`, `lockdown_device(device, keep)` and `set_mode(home_mode)` are offered alongside the reads. A model message with any write call ends the turn there: more than one write, or arguments that don't match `WRITE_TOOLS`' schema exactly (`ollama_agent.valid`, no coercion; plus an exact domain and at least one name word), gets a fixed "nothing changed" reply with no retry. A valid call is mapped by `propose` onto the same `(kind, args, prompt)` voice commands use (`allow_request`, `lockdown_request` with the model's keep list, and new `block` and `home_mode` risky actions) and handed to `voice_agent.confirmation`, so it runs only on a spoken yes, through `add_rule` (`created_by: voice`, on the undo stack). `block` refuses a domain on or under an `allowlist.txt` entry, because a global block rule beats the allowlist; voice's own block command does too. A final text reply that claims a change is replaced with "I haven't changed anything".

`voice_agent.respond` keeps its order: service and wildcard allows, lockdowns and away mode on or off (which only ask for confirmation), confirmations, home-mode writes, block commands, single-domain allows, undo, then requests with write words the router can't parse (a block or allow without a domain or service, "lock down the TV to Netflix"), which go to the model first and fall back to the clarifying question or "nothing changed" reply, the deterministic "what they know" and greeting replies, then the model (`voice_agent.ask_model`), then the keyword fallbacks. `frontend/serve.py` turns the model on at startup (`voice_agent.ask_model` and `voice_agent.phrase_inferences`) unless `EDDIE_AGENT=off`; `EDDIE_OLLAMA_URL` (default `http://127.0.0.1:11434`) and `EDDIE_AGENT_MODEL` (default `llama3.2:3b`) configure it. Typed asks and speech use the same path. Checked against `llama3.2:3b` on the development Mac with seeded traffic: 2 to 7 s an answer, and "What's the TV doing?" gave the Fire Stick's real counts. The 3B model can still pin a real number on the wrong device or call something "none" (see PRIVACY.md); unit tests use a stubbed model.

## Voice block command (#11)

`voice_agent.block_target` matches a whole utterance of the form "(please / can you) block <it | that | this one | that tracker | domain> (please / now)" after lowercasing and turning a spoken "dot" into ".". Negations, questions and extra requests ("block it and email Will") don't match. `resolve_it` uses the last domain named in one of Eddie's replies this conversation (`voice_agent.context`, cleared by `forget_conversation` on dismissal and mic stop), else the newest `flag` row, or `allow` row whose category is telemetry, ads, analytics or tracking, in the last 15 minutes of `GET /events`. An unresolvable "it" or a non-domain target ("block Netflix") asks for the domain and sends nothing. `block_domain` posts `{pattern, action: block, created_by: voice}` with no device, so the rule covers every device, and waits up to 5 s. The rule counts as stored only when the reply echoes an integer `id`, the same pattern and `action: block`; anything else, an HTTP error or a timeout is spoken as "I couldn't add that rule. Nothing changed." `applied: true` is spoken as blocked and loaded by Eddie's DNS; `applied: false` as saved but not yet loaded, so it may still get through. No read-back confirmation: the rule is reversible with `DELETE /rules/{id}`, which voice undo uses (below).

## Voice allow command (#13)

`voice_agent.allow_target` shares block's whole-utterance parsing (`command_target`) and classifies the target as a service (an alias in `voice/services.json`, the one service map), one exact domain, a typed `*.a.com` wildcard, or unknown. Services and wildcards go through `Confirmation` as the `allow` action; on yes, `allow_patterns` posts one global allow rule per pattern in order through the same `add_rule` check as block (integer `id`, echoed pattern and action), stopping at the first failure and saying how many were saved. The last rule's `applied` stands for the set, since the DNS engine loads whole revisions. An exact domain is posted straight away. Unknown targets get a clarifying question naming the known services, and nothing is sent. See [voice/README.md](../voice/README.md#allow-a-service-or-domain-13).

## Voice lockdown (#17)

`voice_agent.lockdown_target` matches a whole utterance "(please / can you) lock down <the | my | our> <device> (please / now)"; extra requests and keep lists ("lock down the TV and the iPad", "lock down the TV to Netflix") don't match and change nothing. `lockdown_request` reads `GET /devices` and matches the spoken name against user labels only (vendor names and IPs aren't things people say): an exact label first, else labels that contain the words. No match lists the labelled devices and asks for a label; two or more ask which one; a device that already has a `*` rule (`GET /rules`) is reported as locked down. None of these send a write. One match goes through `Confirmation` as the `lockdown` action with the device key, its name and `LOCKDOWN_KEEP` (every service in `voice/services.json`).

On yes, `lockdown_device` posts one device allow rule per keep pattern, then the device block rule `*` last, each through `add_rule`'s check (integer `id`, echoed pattern, action and `device_mac`). Ordering the block last means a failure partway never leaves the device blocked without its keep list. On any failure the saved rules are deleted again newest first; ones whose delete fails stay on the undo stack, and the reply says how many were saved and whether they were removed. On success the whole set goes on the undo stack as one command. The last rule's `applied` stands for the set; success is spoken as "rules saved and loaded", never as traffic seen blocked, because a device that doesn't use Eddie for DNS is unaffected.

The `*` rule is only accepted for one device and only as a block (`rules.RuleIn`). `decision.RuleIndex.find` treats it as the least specific device rule: the device's own rules beat it, and it beats global rules. When it is the match, an allowlisted domain is still allowed (source `allowlist`), so sign-in, updates, time and captive-portal checks survive; everything else is blocked with reason "device lockdown". See [voice/README.md](../voice/README.md#lock-down-a-device-17).

### Voice undo (#15)

`add_rule` appends each acknowledged voice rule (`id`, pattern, action, `ts`) to the command's list, and `remember_rules` pushes that list onto `voice_agent.undo_stack` (memory only, newest last, at most 20 commands, not cleared by `forget_conversation`). "Undo" (`UNDO`, whole utterance) runs `undo_command`: it reads `GET /rules` once, then deletes the newest entry's rules newest first with `DELETE /rules/{id}`. An id is deleted only while its row still matches the stored pattern, action and `ts` with `created_by: voice`, because the `rules` table's plain `INTEGER PRIMARY KEY` lets SQLite reuse a deleted top id; a row that's gone or changed, or a 404, counts as already removed and is dropped, never retried. A delete counts only if the reply echoes the id with `deleted: true`; the last delete's `applied` stands for the set. On a backend failure the remaining rules stay on the stack. A rule changed between the list read and its delete is still possible but narrow. See [voice/README.md](../voice/README.md#undo-the-last-voice-rule-15).

## Confirmation state

Risky tools go through a single pending-action slot in `voice/voice_agent.py` (`Confirmation`). A command only creates `{kind, args, prompt, expires_at}` and speaks a read-back; the action runs only when the next reply is an exact yes phrase within 15 seconds. No, cancel, a second unclear reply, expiry, conversation dismissal and microphone stop or error all discard it; a new risky command replaces it and says so. Ambiguous input and timeouts never execute. The bridge emits `voice_state: confirming` (`kind`, `prompt`, `expires_in_ms`; no arguments) after the read-back so the screen can ask for yes or no. Actions are registered in `RISKY_ACTIONS` and parsed by `RISKY_COMMANDS`. The actions today are `allow` (#13), for a named service or a typed wildcard, and `lockdown` (#17). Both are parsed in `route` rather than `RISKY_COMMANDS`: that list sees text without dots, and lockdown needs a `/devices` lookup that can answer with a question instead. `RISKY_COMMANDS` stays empty until email exists. See [voice/README.md](../voice/README.md#confirmation-for-risky-actions) for the reply table.

## DNS server status

`eddie/dns_server.py` answers UDP DNS on port 53 with asyncio and dnslib. Each query goes through `decision.evaluate(domain, device, client_ip)`, where `device` is the MAC `eddie/devices.py` found for the client IP in the ARP table, or the IP itself while it's unknown; a device rule matches either. Blocked queries get `0.0.0.0` / `::` (TTL 60, empty answer for other types). Allowed queries are forwarded as raw packets to each upstream in turn (2 s timeout each), and the answer is returned unchanged. If every upstream fails, the device gets SERVFAIL. Non-DNS packets are dropped, and at most 512 lookups are in flight. The decision path makes no model or network calls. Not built yet: TCP (truncated answers can't be retried over TCP).

`eddie/feed.py` sends each decision to the live feed (#16). `resolve` builds a `query` event (docs/EVENTS.md) and puts it on a bounded in-memory queue (1,000 events); one sender thread posts batches of up to 100 to `POST /ingest` with a 1 s timeout. If the API is down, slow or answers an error, the batch is dropped and counted, never retried, and one warning is logged until it's reachable again: the feed is a live view, and `eddie.db` is the history. Network plumbing (`decision.is_plumbing`: `*.arpa` reverse lookups, `_`-prefixed service-discovery names, `.local` and single-label names) is not sent, and a repeat of the same device, domain and action within 2 s is merged into the first event (a browser's A and AAAA pair is one line). Both are still answered and logged; the merge memory is at most 10,000 keys. On a real Mac on a campus network, plumbing and A/AAAA pairs were most of the feed before this. The query log and the feed are independent, so either can be off. Measured on the development Mac: a lookup reaches `/ws/events` in about 6 ms (blocked) to 25 ms (forwarded), and an unreachable API adds nothing to DNS replies (tested). The event's `device_mac` is the device's MAC and `device` its name (label, DHCP hostname, or "<vendor> device"), both from `DeviceMap`'s in-memory snapshot; a client with no MAC yet is `ip:<client IP>` with the IP as its name. A new label reaches the feed at the next ARP read (at most 30 s). `scripts/fake_traffic.py` is unchanged and posts the same format, so it stays the replay fallback; run one sender at a time or the feed mixes both.

`eddie/decision.py` applies README "Decision order" from in-memory snapshots only (no disk, model or network on the hot path; median about 4 µs a lookup on the development Mac with 150k blocklist entries and 1,000 rules). Writers replace whole snapshots: `set_lists` (called once at DNS startup with `eddie/lists.py`), `set_rules` and `load_from_store` (rules and `ai_verdicts` from `eddie.db`). List entries cover their subdomains; a rule pattern `a.com` is exact and `*.a.com` covers a.com and its subdomains, with the most specific rule winning, then the newest. The short keywords `ads` and `log`/`logs` must be a whole word in a label so `uploads`, `blog` and `login` aren't blocked. Unknown domains are flagged and forwarded; one the device looks up on a regular timer is flagged with source `heuristic` and a "looked up every N s, likely telemetry" reason instead (see "Beacon and idle detection" below). A cached AI verdict never blocks on its own: `needed` allows, `tracker` flags with the reason `likely tracker: …`, `unsure` flags. On real traffic from the development Mac, `llama3.2:3b` labelled `www.gstatic.com`, Google image thumbnails, Apple's update catalog, Safe Browsing and `one.one.one.one` trackers at 0.8–0.9 confidence, so confidence doesn't separate good verdicts from bad ones. Blocking an AI-flagged domain takes a user rule: "block it", or a yes to Eddie's question about it (#79, "Ask before blocking" below). The DNS server's `StoreWatcher` checks `eddie.db` every 0.2 s in a worker thread (a cheap count and max-timestamp query on `rules` and `ai_verdicts`, plus the `rules_rev` counter) and calls `load_from_store` only when one changed, so rules and verdicts written by other processes take effect within about 0.2 s. After each reload it writes the rules revision it loaded to `engine_state.rules_loaded`.

Away mode (#109, `eddie/away.py`): `POST /mode {"away": true}` ranks devices from the last week of the query log in a worker thread on a read-only connection (interim occupancy leak score: hours with media lookups or 3× bursts; security devices exempt), stores them in `away_devices` with `away`, `away_until` and `away_rev` in `engine_state`, and waits for `away_loaded`. The watcher also checks `away_rev`; `load_from_store` hands the engine a frozen `Away(devices, until)` snapshot, and the engine checks the end time per lookup, so expiry needs no reload. For covered devices only, after the keyword step, labelled telemetry domains, AI tracker verdicts and beacons are blocked with source `away_mode`. The covered set is fixed when away turns on; a device that appears later isn't added. Tested end to end against a real DNS server (`tests/test_away.py`); not yet run on the household's real traffic, so how many devices the interim score covers there is unverified.

Offline mode (#26, `eddie/offline.py`): the watcher also checks `engine_state.offline_rev`, switches `dns_server.offline_mode.on` to the stored `offline` value, and writes `offline_loaded`, which `POST /offline-mode` waits for. While online, every upstream answer except SERVFAIL is kept as raw bytes in an in-memory cache keyed by name, type and class (4,096 answers, oldest dropped). While offline, `resolve` never calls `forward`: allowed lookups get the cached answer with the request's ID and question and TTLs aged (30 s once expired, nothing past 24 h), or SERVFAIL; blocked lookups are unchanged. The API, dashboard, classifier (Ollama) and voice all talk to `127.0.0.1` or IP literals, so they don't depend on upstream DNS. Tested with a fake upstream that counts packets (`tests/test_offline.py`); not yet checked on hardware with the uplink actually unplugged. Offline mode stops Eddie's DNS forwarding only: in router mode it doesn't stop packet forwarding, so a device using hard-coded IPs or its own DNS (DoH) still reaches the internet.

`eddie/devices.py` (#14) keeps the IP → MAC map for DNS. The lookup only reads an in-memory dict. A background task checks every second and reads the ARP table (`ip neigh show` on Linux, `arp -an` on macOS, 2 s timeout) in a worker thread when a client IP has no MAC or hasn't been recorded yet, and otherwise every 30 s. Each read upserts the devices that looked something up since the last read into `devices` (ip, vendor, DHCP hostname, first and last seen; never the label). An IP ARP can't resolve triggers one read, not one per lookup. Vendors come from `eddie/data/oui_vendors.json`, built at setup by `scripts/build_oui.py`. `GET /devices` joins `devices` with per-device counts from `queries`; `PUT /devices/{mac}` writes the label. If ARP can't be read, every device stays keyed by IP and DNS is unaffected.

`eddie/rules.py` and the API's `/rules` endpoints (#12) are the rule writers. Each add or delete stores the row and bumps `engine_state.rules_rev` in one transaction, then the API waits up to 2 s for `rules_loaded` to reach that revision and returns `applied: true` only if it did. That is the DNS engine's acknowledgment, not just a stored row: once `applied` is true the very next lookup Eddie answers uses the change, and Eddie keeps no decision cache. Devices still cache earlier answers for their TTL (60 s for blocks, upstream's TTL for allowed answers), so a device may not ask again straight away. `applied: false` means the rule is stored but no running DNS server loaded it in time (DNS stopped, `EDDIE_DB` pointing at another file, or the API in Docker on a Mac while DNS runs on the host: the container has its own `eddie.db`). Voice must say so rather than claim the block worked. Each stored add or delete is also broadcast on `/ws/events` as `rule_change` (#7), before the wait, so it reports the stored row and never enforcement. The event and `GET /rules` carry the device's display name; the dashboard shows each change as a feed row and toast and lists active rules through `serve.py`'s read-only `GET /api/rules` relay (#19).

Spoof rules (#99): `decision.py` passes a rule's `spoof` action through like `allow` and `block`. `resolve` answers it with `EDDIE_SPOOF_IP` for A (TTL 60) and an empty answer for every other type, so IPv6-capable clients fall back to the A. If `EDDIE_SPOOF_IP` is unset, the spoof is answered as a block. `eddie/spoof_server.py` is a separate asyncio process (port 80, `EDDIE_SPOOF_PORT`) that reads a request head of up to 16 KB, drains and drops up to 1 MB of body, and answers `200 OK` with `Content-Length: 0`. It doesn't do TLS. The dashboard turns the house icon into Pinocchio while `GET /rules` holds any spoof rule; that is stored rules, not proof the stub server is running. Tested: decision path, DNS answers with and without the IP, rule validation, stub responses (GET, drained POST, oversized head, hang-ups) and that the stub logs nothing per request. Not tested on the Pi with a real device.

`eddie/lists.py` reads every `blocklists/*.txt` (hosts format or one domain per line; comments, IPs and hosts-file names such as `localhost` and `broadcasthost` are skipped) and `allowlist.txt`. A missing allowlist stops startup. The allowlist is kept narrow (exact hosts or single-purpose zones such as `nflxvideo.net`, never `amazon.com`), and a test fails if any allowlist entry would unblock a domain on the shipped blocklists. That's why the Prime Video zones `aiv-delivery.net` and `pv-cdn.net` aren't on it: StevenBlack blocks one host in each. The same rule keeps the Google shared-infrastructure entries host by host (`www.gstatic.com`, `encrypted-tbn0..3.gstatic.com`, `lh3.googleusercontent.com`): StevenBlack blocks `csi.gstatic.com` and some `googleusercontent.com` ad hosts. `blocklists/eddie-extra.txt` is Eddie's own short list of measurement-only hosts seen on real traffic that no shipped list blocks (GitHub's `collector.github.com`, Notion's Splunk intake, Google's `adtrafficquality.google`, ChatGPT's A/B-testing host, Cloudflare error reports). PerimeterX bot detection (`protechts.net`, `px-cloud.net`) is deliberately not on it: blocking it can make sites challenge or refuse the user. Lists change only on restart.

`eddie/classifier.py` runs separately from DNS. Its prompt tells the model that shared infrastructure (static-file and image hosts, CDNs, cloud hostnames, DNS resolvers, safety checks) is `needed` even when the owner also runs ads, and that a wrong `tracker` is worse than `unsure`, with eight labelled examples. On 38 hand-labelled domains from real Mac traffic it called infrastructure a tracker 2 times out of 28 (5 with the old prompt) and caught 6 of 10 trackers (same as before); the examples share some patterns with that set, so treat it as a smoke test, not a benchmark. Flagged query rows are its durable queue. Network plumbing (`decision.is_plumbing`: reverse lookups, service discovery, `.local`) is never queued. The production loop schedules at most two HTTP inference requests concurrently, oldest observed first, and polls futures every 250 ms without waiting for a model. Each request has a seven-second socket timeout and bounded output tokens; load, backlog and cold starts can still miss the ten-second target. No model is called by DNS. Inputs are domain, optional friendly device label, ten-minute lookup count and idle (no allowed, labelled media traffic in five minutes; unknown without media history). Strict validated JSON is cached in `ai_verdicts`, then DNS's watcher reloads it. Invalid output backs off for five minutes; unavailable inference backs off for ten seconds. A bounded in-memory event outbox retries local API delivery without rerunning inference. Restart can lose undelivered events, but cached verdicts remain authoritative. The initial #27 implementation is retained through its synchronous compatibility interface and tests.

`eddie/store.py` owns `eddie.db` (path from `EDDIE_DB`) and creates the README schema on first open (WAL mode, so readers don't block the writer). Every parsed DNS question writes one `queries` row with only ts (ms, arrival), device (MAC from `devices.py`, or the client IP if unknown), domain, qtype, action, source and reason; SERVFAILs are logged with the decision that was made, and non-DNS or question-less packets are not logged. The DNS task only puts the row on a bounded in-memory queue (10,000 rows); one writer thread batches inserts. If the writer falls behind, rows are dropped and counted rather than slowing DNS. Ctrl-C and SIGTERM flush the queue before exit; a hard kill loses at most the unflushed rows. Privacy measures: rows older than `EDDIE_RETENTION_DAYS` (default 7) are pruned at start and hourly with `secure_delete` plus a WAL truncate; the database files are `0600`; `EDDIE_DB=off` disables the log. The API reads it for `/devices` counts and recent blocked domains and for the live "what they know" report (`GET /what-they-know` opens its own read-only connection in the thread pool and loads the window's rows, falling back to the in-memory feed when the log has none); the live feed is still the API's own in-memory list, which drops events older than `EDDIE_RETENTION_DAYS` on every ingest and read (#129). Encryption at rest is a filesystem-level setup step on the Pi (a LUKS volume holding `EDDIE_DB`), not code; see PRIVACY.md. Every privacy decision and known gap is tracked in [PRIVACY.md](PRIVACY.md).

## Traffic monitor (#136)

`eddie/traffic.py` is an optional, separate process (`python -m eddie.traffic`); the DNS server never imports it, so DNS never waits on it. It is off until started with `EDDIE_TRAFFIC_IFACE` (or `--iface`), and refuses to start with `EDDIE_DB=off`. Live capture opens a Linux `AF_PACKET` raw socket on the LAN interface (root or `CAP_NET_RAW`) and reads at most 128 bytes of each frame, enough for Ethernet, 802.1Q, IPv4 / IPv6 and TCP / UDP headers; there is no scapy dependency. `--pcap FILE` replays a classic Ethernet pcap instead (any OS).

Direction comes from Eddie's own MAC on that interface (`/sys/class/net/<iface>/address`, or `--router-mac`): a frame to it is a device's upload, a frame from it a download. The device is the other MAC; the remote is the far IP and port, and only global addresses count, so Eddie's own DNS replies and device-to-device traffic are skipped. Without the router MAC (pcap replay) it falls back to "one side local, the other global", which misses IPv6 devices with global addresses. Bytes are the IP header's length field (headers plus payload as sent). Later IPv4 fragments and IPv6 extension headers are counted with port 0.

Counts stay in memory (at most 10,000 flows; new flows past that are dropped and counted) and are written to `traffic` every 60 s and on exit (Ctrl-C, SIGTERM), then pruned with the query log (`store.prune`, by `last_ts`). Tested against a hand-built fixture capture (`tests/fixtures/traffic.pcap`, checked with `tcpdump -r`) in `tests/test_traffic.py`.

Limits: it only sees other devices' packets when Eddie is their router (#22, not built yet). On the hotspot setup devices send packets straight to the iPhone, so the monitor sees only Eddie's own traffic and records nothing useful; Wi-Fi monitor mode isn't used. Live capture has not been run on the Pi yet. Nothing reads `traffic` yet: mic watch, camera watch and bypass detection are the planned consumers, and there is no API endpoint. nftables counters (kernel-side, no per-packet Python) are the alternative if per-packet parsing proves too slow on the Pi.

```bash
sudo EDDIE_TRAFFIC_IFACE=wlan0 .venv/bin/python -m eddie.traffic            # Pi in router mode
uv run python -m eddie.traffic --pcap capture.pcap --router-mac 02:ed:d1:e0:00:01  # replay, any OS
```

## Dashboard bridge control (#40)

`frontend/serve.py` serves the page, the `/events` SSE stream and read-only GET endpoints such as `/api/voice/status` to anyone who can reach it; with `--host 0.0.0.0` that includes the iPad. Control routes are POSTs and pass three checks in order:

1. **Host.** The `Host` header must be an IP literal, `localhost` or a `.local` mDNS name, so a DNS-rebound domain can't reach loopback controls from a browser. Then the existing same-origin check rejects cross-origin browser requests.
2. **Loopback is trusted.** Requests from the Eddie computer itself need no token.
3. **Other devices need the pairing token and only reach `/api/voice/ask` and the mode toggles (`/api/mode`, `/api/offline-mode`, #35).** The token comes from `EDDIE_DASHBOARD_TOKEN`, or is random (`secrets.token_urlsafe`) on each start. When bound beyond loopback, `serve.py` prints `http://<LAN IP>:5173/#pair=<token>`. The page sends it as `Authorization: Bearer <token>` (constant-time compare). A missing or wrong token gets 401. `/api/voice/start`, `/api/voice/stop`, `/api/voice/dismiss` and `/api/events` answer 403 from any other device, with or without the token: the microphone is never switched from the network, and traffic events only come from this machine.

The token is in the URL fragment, which browsers don't send, so it isn't in request lines or access logs, and the page keeps it nowhere but the URL. A random token changes on restart, so set `EDDIE_DASHBOARD_TOKEN` for a Home Screen link that survives restarts. There is no typed-ask box in the page yet; `window.eddie.ask(text)` is the client hook. The traffic API on port 8000 is separate: its writes need `EDDIE_API_TOKEN` from anywhere but loopback and its WebSocket checks `Origin` (#96, docs/EVENTS.md), but its reads are open.

The mode toggles (#35) relay one boolean to `POST /mode` or `POST /offline-mode` and return the API's own answer; the page shows a toggle's new state only from that answer or from the API's `mode` / `offline_mode` broadcasts, and offline mode's `applied: false` as "not yet applied by DNS". Home mode is a backend flag the DNS server doesn't enforce yet, and the page says so whenever it is on. Away mode has no toggle; the page shows a note only from `GET /mode` or the `away_mode` broadcast with `away_applied: true` (covered devices and the security devices that stay up), "not yet applied by DNS" in red otherwise, and drops the note at `away_until`.

## Ask before blocking (#79)

`eddie/questions.py` turns AI `tracker` verdicts posted to the API into questions, in the API's memory: one open at a time, a new one at most every 180 s, waiting trackers grouped by device (at most five a question), each domain offered once per API run. `POST /questions/{id}` answers Block / Allow with one global rule per domain through the same store and DNS handshake as `POST /rules`, or Ignore with nothing. The dashboard card answers through the bridge (`by: dashboard`) and its Undo deletes just those rules; the voice worker reads an open question when woken (`serve.py` calls `question_announcement` on the `wake` event, before listening), and a yes runs `answer_question` (`by: voice`), which goes on the voice undo list. Both say blocked only on `applied: true`. Not built: the opt-in to ask unprompted, and the idle-device detector as a question source. Contract in docs/EVENTS.md.

## Beacon and idle detection (#24)

`eddie/beacons.py` holds the timing evidence. `Beacons` keeps the last 12 lookup times for each device and domain (at most 10,000 pairs, least recently seen dropped); lookups within 2 s of the previous one, such as an A and AAAA pair, count once. With at least 5 gaps, a mean gap between 10 s and 1 h and a gap coefficient of variation of at most 0.15, the pair is a beacon at that mean interval. `Idle` keeps each device's latest allowed media lookup (`labels.HUMAN`); a lookup is idle when that was 5 minutes or more before it, and unknown (`null`) if the device has had none.

- Decision engine: only lookups that reach the unknown step are timed, so listed, ruled and classified domains cost nothing extra. A beaconing unknown is flagged with source `heuristic`, and the classifier's queue takes flagged `heuristic` rows as well as `default` ones. The DNS server passes each lookup's arrival time.
- Events: the API runs its own `Beacons` and `Idle` over `/ingest` events, keyed by `device_mac`, and adds `beacon_s` and `idle` to each event (docs/EVENTS.md). This covers blocklisted and allowed domains too.
- "What they know": `inferences.beacon_fact` replays the window through a fresh `Beacons` and reports the device and domain with the most lookups made on a timer, listed or not.

Limits: devices cache answers, so a timer only shows at DNS level when the domain's TTL is shorter than the timer. A device's history restarts when its key changes from IP to MAC and when a process restarts. The thresholds are tuned on synthetic traffic and the scripted feed, not on captured Fire Stick traffic. Beacons only flag; they never block on their own.

## Bypass detection (#97)

`eddie/bypass.py` holds `RESOLVERS`, encrypted DNS resolver names (DoH, DoT and Android Private DNS) seeded from the curl wiki's public resolver list, Chromium's DoH provider table and Firefox's default providers; an entry covers its subdomains. The API's `/ingest` runs each query event through `bypass.Suspicions` after broadcasting it and pushes `bypass_suspected` (device, name, provider, `blocked`) once per device and name every 10 minutes, so detection stays off the DNS hot path. `EDDIE_BLOCK_DOH=on` sets `decision.engine.block_doh` at DNS startup, which blocks those names after the blocklist step; rules and the allowlist still win. Blocking a name only stops clients that set their resolver up by name; one that has the resolver's IP still skips Eddie, and nothing here detects that. Not built: flagging a device that goes quiet on DNS while clearly active (Eddie only sees DNS, so it can't yet tell "active"), and DoT on port 853 to hard-coded IPs (needs router mode). Tested in `tests/test_bypass.py` and the dashboard event test; not yet checked against a real Android Private DNS or browser DoH setting on hardware.
