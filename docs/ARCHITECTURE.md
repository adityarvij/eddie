# Eddie architecture: voice implementation status

The backend API and DNS enforcement are independent of the voice worker. Development currently uses the Mac microphone and a localhost dashboard; production should run the same offline worker on the final box after ARM64 performance checks.

Audio → openWakeWord custom ONNX → bounded in-memory capture → faster-whisper local model → deterministic tool router → local REST API → Piper → audio output.

The dashboard bridge publishes `voice_status`, `wake`, `voice_state`, `transcript`, `agent_reply`, `speaking`, and `speech_end` events through its existing SSE connection. It accepts start, stop and typed ask requests. Speech and typed responses share a serialized lock. Recognition discards input during replies and resets detector history before rearming.

Implemented tools are backend summary reads, “what they know” inference reads (`what_they_know` → `GET /what-they-know`) and home-mode writes. Inferences are deterministic facts from the event log (including sessions of one category with gaps under 10 minutes, and category by weekday), each tagged with one of the README's ten report categories and `sensitive` for Health, Beliefs and Kids (#134). The router honors explicit ranges such as “the last 3 days” or “two weeks”; with no range it requests all locally retained history. The API caps longer requests to `EDDIE_RETENTION_DAYS`, discloses the cap, and returns `enough_data: false` rather than offering an inference with fewer than two observations. When the local model is on, `ollama_agent.phrase` writes at most five "Someone could guess …, because …" lines from the facts alone (no tools, one call, 20 s limit); lines with a number, clock time or weekday not in the facts are dropped, and the backend template is spoken if none survive or the model is down. On the development Mac with `llama3.2:3b` and the demo week this took 4 to 9 s, and each kept line quoted its evidence; the check cannot catch a misread fact. `GET /what-they-know?demo=true` runs the same code on a seeded, labelled demo week (`eddie/demo_week.py`); the dashboard shows it under a DEMO DATA banner and voice never reads it. The burglar's-eye report (`burglars_eye` → `GET /burglars-eye`, `eddie/occupancy.py`, #34) is deterministic too: it buckets the window into local hours (busy if any device streamed, quiet if not, absent if nothing was looked up), reports waking stretches quiet on most days seen, ranks devices by occupancy leak score, and flags camera, doorbell and alarm devices `never_block` (advice only until #46). It defaults to a week, takes the range from the question with the same parser and retention cap as "what they know", says when the data covers less than that ("from recent data"), and says so instead of concluding when there is too little. Home-mode writes are reported as enforced only when `/mode` answers `home_applied: true` (DNS loaded it). Missing tools explicitly report that no change occurred. The model does not fabricate counts. Ollama tool calling (#29) sits on that boundary for read-only questions; see below. Lockdown (#17) and away mode (#109) use the confirmation state below; email will too.

## Local tool-calling agent (#29)

`voice/local_intent.py` (#179) is a read-only fast path before the tool-calling agent. At dashboard startup it loads the provisioned all-MiniLM-L6-v2 ONNX model and tokenizer, embeds fixed example phrasings once, and cosine-matches each otherwise-unhandled transcript against four intents: device activity, overall summary, recent blocks and why a domain was blocked. The model selects only the intent; device and domain slots use `ollama_agent`'s deterministic parsers, and answers are the tools' code-built `said` sentences. A score below 0.56 returns `None` to the existing Ollama/keyword path. Commands and confirmations run earlier in `voice_agent.route`, so semantic matching has no write path. Model files are revision- and SHA-256-pinned in `voice/assets.json`, fetched only by `scripts/provision_voice.py`, and never downloaded at runtime.

`voice/ollama_agent.py` runs a bounded Ollama `/api/chat` loop (temperature 0, at most 4 model calls and 30 s per question, 20 s per call) with the README system prompt and five read-only tools: `get_summary` (`GET /summary?window=` per-device counts, plus one factual sentence per device for the model to repeat), `get_recent_blocks` (`GET /events?action=block`), `explain_domain` (latest `/events?domain=` row and any `/ai/verdicts` entry), `what_they_know` and `burglars_eye`. Spoken device names are matched leniently ("the TV" matches a Fire Stick, Roku or Chromecast label); an unknown name returns the known devices to the model. Argument errors go back to the model; a backend failure ends the turn with a fixed "can't reach the backend" line. The reply is checked so every number in it appears in the turn's tool results; otherwise Eddie falls back to backend text or says it can't verify. If Ollama is down, slow or loops, `answer` returns `None` and the deterministic keyword router answers instead.

Write tools (#108): `block(domain)`, `allow(service | domain)`, `lockdown_device(device, keep)` and `set_mode(home_mode)` are offered alongside the reads. A model message with any write call ends the turn there: more than one write, or arguments that don't match `WRITE_TOOLS`' schema exactly (`ollama_agent.valid`, no coercion; plus an exact domain and at least one name word), gets a fixed "nothing changed" reply with no retry. A valid call is mapped by `propose` onto the same `(kind, args, prompt)` voice commands use (`allow_request`, `lockdown_request` with the model's keep list, and new `block` and `home_mode` risky actions) and handed to `voice_agent.confirmation`, so it runs only on a spoken yes, through `add_rule` (`created_by: voice`, on the undo stack). `block` refuses a domain on or under an `allowlist.txt` entry, because a global block rule beats the allowlist; voice's own block command does too. A final text reply that claims a change is replaced with "I haven't changed anything".

`voice_agent.respond` keeps its order: deterministic command parsers and confirmations, deterministic reports, greetings, then the MiniLM factual-intent path. A command the parsers cannot understand says nothing changed; an unmatched question gets a short list of supported capabilities. `frontend/serve.py` loads MiniLM when its provisioned files exist. Ollama is off by default, so neither ordinary answers nor "what they know" phrasing call it; `EDDIE_AGENT=ollama` explicitly restores the optional `voice_agent.ask_model` and `voice_agent.phrase_inferences` fallbacks. `EDDIE_OLLAMA_URL` and `EDDIE_AGENT_MODEL` configure that opt-in path. Typed asks and speech use the same router. MiniLM timing on the Pi 5 is still a hardware check and is not inferred from development-host tests.

## Voice block command (#11)

`voice_agent.block_target` matches a whole utterance of the form "(please / can you) block <it | that | this one | that tracker | domain> (please / now)" after lowercasing and turning a spoken "dot" into ".". Negations, questions and extra requests ("block it and email Will") don't match. `resolve_it` uses the last domain named in one of Eddie's replies this conversation (`voice_agent.context`, cleared by `forget_conversation` on dismissal and mic stop), else the newest `flag` row, or `allow` row whose category is telemetry, ads, analytics, tracking or id-sync, in the last 15 minutes of `GET /events`. An unresolvable "it" or a non-domain target ("block Netflix") asks for the domain and sends nothing. `block_domain` posts `{pattern, action: block, created_by: voice}` with no device, so the rule covers every device, and waits up to 5 s. The rule counts as stored only when the reply echoes an integer `id`, the same pattern and `action: block`; anything else, an HTTP error or a timeout is spoken as "I couldn't add that rule. Nothing changed." `applied: true` is spoken as blocked and loaded by Eddie's DNS; `applied: false` as saved but not yet loaded, so it may still get through. No read-back confirmation: the rule is reversible with `DELETE /rules/{id}`, which voice undo uses (below).

## Voice timers and reminders (#122)

`voice_agent.route` hands every utterance to `timers.handle` after a pending confirmation has had its chance and before home mode, block, allow and the local model. It matches whole utterances (set a timer, remind me, list, cancel), so they never reach Ollama or the traffic API. `voice_agent.timer_store` is in memory by default; `frontend/serve.py` replaces it with a store backed by `EDDIE_TIMERS_FILE` and starts `ring_timers`, a daemon thread that checks once a second, takes due items out of the store (and the file) and calls `answer(text, reply=str, alarm=title)`. `answer` plays `timers.play_alarm()` under the same voice lock and `speaking` flag as replies, so the microphone ignores the alarm, then speaks. Due times are wall-clock epoch seconds, so they survive a restart; anything overdue rings on the first check with a "Sorry, I'm late" line.

## Voice house guide (#165)

`voice_agent.route` calls `house_guide.answer(raw, profile.role())` right after `timers.handle`, unless the text is a what-they-know, empty-house or privacy-tips question. `house_guide.load` reads `EDDIE_HOUSE_GUIDE` (default `voice/house_guide.json`) on every call and validates it strictly; entries are owner-only unless `audience: guest`. `answer` returns None for anything that isn't a house question, so the router carries on. Otherwise it filters entries to what the role may hear (guest unless the role is exactly `owner`), scores each by the words of its keywords the question mentions, and quotes the single best answer, asks which on a tie, or says it doesn't know. The model never sees the guide. The role comes from Guest Mode (#163): `owner` while it's off, `guest` while it's on, and then the guide also needs the owner's `house_guide` approval.

## Voice allow command (#13)

`voice_agent.allow_target` shares block's whole-utterance parsing (`command_target`) and classifies the target as a service (an alias in `voice/services.json`, the one service map), one exact domain, a typed `*.a.com` wildcard, or unknown. Services and wildcards go through `Confirmation` as the `allow` action; on yes, `allow_patterns` posts one global allow rule per pattern in order through the same `add_rule` check as block (integer `id`, echoed pattern and action), stopping at the first failure and saying how many were saved. The last rule's `applied` stands for the set, since the DNS engine loads whole revisions. An exact domain is posted straight away. Unknown targets get a clarifying question naming the known services, and nothing is sent. See [voice/README.md](../voice/README.md#allow-a-service-or-domain-13).

## Voice lockdown (#17)

`voice_agent.lockdown_target` matches a whole utterance "(please / can you) lock down <the | my | our> <device> (please / now)"; extra requests and keep lists ("lock down the TV and the iPad", "lock down the TV to Netflix") don't match and change nothing. `lockdown_request` reads `GET /devices` and matches the spoken name against user labels only (vendor names and IPs aren't things people say): an exact label first, else labels that contain the words. No match lists the labelled devices, counts the unnamed ones (shown as `---` on the dashboard) and asks for a name; two or more ask which one; a device that already has a `*` rule (`GET /rules`) is reported as locked down. None of these send a write. One match goes through `Confirmation` as the `lockdown` action with the device key, its name and `LOCKDOWN_KEEP` (every streaming service in `voice/services.json`), or `KID_KEEP` (`voice/kid_safe.json`) for a device `GET /devices` marks `kid`.

On yes, `lockdown_device` posts one device allow rule per keep pattern, then the device block rule `*` last, each through `add_rule`'s check (integer `id`, echoed pattern, action and `device_mac`). Ordering the block last means a failure partway never leaves the device blocked without its keep list. On any failure the saved rules are deleted again newest first; ones whose delete fails stay on the undo stack, and the reply says how many were saved and whether they were removed. On success the whole set goes on the undo stack as one command. The last rule's `applied` stands for the set; success is spoken as "rules saved and loaded", never as traffic seen blocked, because a device that doesn't use Eddie for DNS is unaffected.

The `*` rule is only accepted for one device and only as a block (`rules.RuleIn`). `decision.RuleIndex.find` treats it as the least specific device rule: the device's own rules beat it, and it beats global rules. When it is the match, an allowlisted domain is still allowed (source `allowlist`), so sign-in, updates, time and captive-portal checks survive; everything else is blocked with reason "device lockdown". See [voice/README.md](../voice/README.md#lock-down-a-device-17).

### Kid mode (#119)

`devices.kid` is a user flag set with `PUT /devices/{mac}` from the dashboard's device list; it writes no rules. `voice_agent.kid_mode_target` matches "turn on / off kid mode", "lock down / unlock the kids' devices" and the like; `kid_mode_request` reads `GET /devices` and `GET /rules`, picks the child's devices not already that way (locked means a device `*` block rule), and queues one `kid_mode` confirmation. `set_kid_mode` runs `lock_device` (the lockdown above, with `KID_KEEP`) or `unlock_device` per device: unlock deletes the `*` block first, so a failure never leaves a device blocked without its keep list, then the device's allow rules for kid-safe patterns. The dashboard calls the same code through the bridge (`POST /api/kid-mode`, `kid_mode_change`) after its own confirm dialog, with `created_by: dashboard`, and nothing goes on voice's undo stack. Kid mode has no state of its own: the dashboard shows it on when every child's device has a `*` rule.

### Guest Mode permissions (#163)

`voice/guest.py` keeps the profile: `active` and the owner's `allowed` subset of `APPROVABLE`; `OWNER_ONLY` categories can never be allowed, and an unknown category is denied even to the owner, so a new tool has to be given one. `voice_agent.profile` is in memory by default; `frontend/serve.py` loads `EDDIE_GUEST_FILE` and serves `GET` / `POST /api/guest` (loopback only). With no speaker identification, `profile.role()` is `guest` whenever Guest Mode is on. `route` calls `profile.check(category)` at the top of each branch before any lookup and returns its fixed refusal; `Confirmation.request` and `Confirmation.reply` check `RISKY_CATEGORIES[kind]`, so a write proposed by the local model and an owner's pending change are both refused to a guest; `ollama_agent.Agent.run_tool` checks `TOOL_CATEGORIES`. In Guest Mode `route` never calls the model, approved timers go to the in-memory `voice_agent.guest_timers` (rung by `ring_timers` too), and the bridge skips the wake-time question. The house guide (#165) is the `house_guide` category and gets `profile.role()`, so owner entries are spoken only while Guest Mode is off. Device controls (#166) will add their tools under the `tv`, `lights` and `thermostat` categories already in the schema. Guest activation by voice, expiry and the guest page are #120.

### Home mode presence (#20)

`eddie/home.py` holds home mode in `engine_state`: `home_mode` (on or off), `home_manual` and `home_rev`. The decision engine loads `home_mode` with the rules and, while it's on, blocks `decision.CAMERA_DOMAINS` (#43) after rules and the allowlist (source `home_mode`). The API's `watch_presence` task (started by its lifespan when `EDDIE_DB` is on) calls `check_presence` every 15 s. State rules:

- Automatic (`home_manual` 0): home mode is on exactly while at least one device marked `phone` was seen in the last 10 minutes. A change is written, waited on until DNS loads it, then sent as a `mode` event with `reason: presence` and `home_applied`.
- Manual (`home_manual` 1): `POST /mode {"home_mode": ...}` (the dashboard toggle, voice) sets the state and `home_manual`. Presence checks change nothing while it holds, so a phone joining during a manual off does not turn it back on, and a manual on stays on after everyone leaves.
- Back to automatic: `POST /mode {"home_auto": true}` clears `home_manual` and sets the state from the phones home right then. Neither the dashboard nor voice sends it yet.

The check reads `home_manual` and the phones and writes in one step with no await between, so a manual change can't be overwritten by a presence result read before it. The state lives in `eddie.db`, so a manual override survives a restart. Enforcement is DNS-only: a camera with a running upload or its own DNS isn't cut off until router mode and nftables (#22/#23). Security devices are exempted (#46): doorbells, outdoor cameras and alarms (detected automatically by label/hostname keywords or explicitly marked with `security = 1` in `eddie.db`) are exempt from home mode camera blocking and keep resolving their upload domains.

### Voice undo (#15)

`add_rule` appends each acknowledged voice rule (`id`, pattern, action, `ts`) to the command's list, and `remember_rules` pushes that list onto `voice_agent.undo_stack` (memory only, newest last, at most 20 commands, not cleared by `forget_conversation`). "Undo" (`UNDO`, whole utterance) runs `undo_command`: it reads `GET /rules` once, then deletes the newest entry's rules newest first with `DELETE /rules/{id}`. An id is deleted only while its row still matches the stored pattern, action and `ts` with `created_by: voice`, because the `rules` table's plain `INTEGER PRIMARY KEY` lets SQLite reuse a deleted top id; a row that's gone or changed, or a 404, counts as already removed and is dropped, never retried. A delete counts only if the reply echoes the id with `deleted: true`; the last delete's `applied` stands for the set. On a backend failure the remaining rules stay on the stack. A rule changed between the list read and its delete is still possible but narrow. See [voice/README.md](../voice/README.md#undo-the-last-voice-rule-15).

## Confirmation state

Risky tools go through a single pending-action slot in `voice/voice_agent.py` (`Confirmation`). A command only creates `{kind, args, prompt, expires_at}` and speaks a read-back; the action runs only when the next reply is an exact yes phrase within 15 seconds. No, cancel, a second unclear reply, expiry, conversation dismissal and microphone stop or error all discard it; a new risky command replaces it and says so. Ambiguous input and timeouts never execute. The bridge emits `voice_state: confirming` (`kind`, `prompt`, `expires_in_ms`; no arguments) after the read-back so the screen can ask for yes or no. Actions are registered in `RISKY_ACTIONS` and parsed by `RISKY_COMMANDS`. The actions today are `allow` (#13), for a named service or a typed wildcard, `lockdown` (#17), and `text` (below). Both are parsed in `route` rather than `RISKY_COMMANDS`: that list sees text without dots, and lockdown needs a `/devices` lookup that can answer with a question instead. `RISKY_COMMANDS` stays empty until email exists. See [voice/README.md](../voice/README.md#confirmation-for-risky-actions) for the reply table.

### Voice texts

`voice/texting.py` parses “text / message / send a text to <contact> <message>” from the raw transcript against `voice/contacts.json` (longest name wins; no spoken numbers) and keeps the rest of the utterance as the message, word for word. `voice_agent.text_request` hands `{name, address, service, body}` to `Confirmation` with a 30 s window; the prompt reads the message back. On yes, `send_text` calls the sender chosen by `EDDIE_TEXTING` (only `messages`, macOS): `MessagesSender` runs `osascript` with the address, message and service as arguments (never interpolated), then polls `~/Library/Messages/chat.db` read-only for up to 10 s for the newest outgoing message to that address since the send. `is_sent` with no `error` is spoken as sent; an error, a nonzero `osascript` exit, no confirmation in time, or an unreadable database each get their own reply, never “sent”. The local model has no texting tool. Linux has no sender yet.

## DNS server status

`eddie/dns_server.py` answers DNS over UDP and TCP on port 53 with asyncio and dnslib. Each query goes through `decision.evaluate(domain, device, client_ip)`, where `device` is the MAC `eddie/devices.py` found for the client IP in the ARP table, or the IP itself while it's unknown; a device rule matches either. Blocked queries get `0.0.0.0` / `::` (TTL 60, empty answer for other types). Allowed queries are forwarded as raw packets to each upstream in turn (2 s timeout each), and the answer is returned unchanged. If every upstream fails, the device gets SERVFAIL. Non-DNS packets are dropped, and at most 512 lookups are in flight. TCP (RFC 7766, #95) is where devices retry an answer that came back truncated over UDP: each query on a connection goes through the same `decision.evaluate`, query log and feed, and allowed ones are forwarded to the upstreams over TCP, so the full answer comes back. At most 64 TCP connections are open (extra ones are closed at once); a connection is closed when the client sends nothing for 10 s, takes longer than that to finish a query or to read a reply, or sends something that isn't DNS. A UDP reply bigger than the client's buffer (512 bytes, or its EDNS size), such as an offline answer first fetched over TCP, is sent empty with the TC flag so the device retries over TCP. The decision path makes no model or network calls.

`eddie/feed.py` sends each decision to the live feed (#16). `resolve` builds a `query` event (docs/EVENTS.md) and puts it on a bounded in-memory queue (1,000 events); one sender thread posts batches of up to 100 to `POST /ingest` with a 1 s timeout. If the API is down, slow or answers an error, the batch is dropped and counted, never retried, and one warning is logged until it's reachable again: the feed is a live view, and `eddie.db` is the history. Network plumbing (`decision.is_plumbing`: `*.arpa` reverse lookups, `_`-prefixed service-discovery names, `.local` and single-label names) is not sent, and a repeat of the same device, domain and action within 2 s is merged into the first event (a browser's A and AAAA pair is one line). Both are still answered and logged; the merge memory is at most 10,000 keys. On a real Mac on a campus network, plumbing and A/AAAA pairs were most of the feed before this. The query log and the feed are independent, so either can be off. Measured on the development Mac: a lookup reaches `/ws/events` in about 6 ms (blocked) to 25 ms (forwarded), and an unreachable API adds nothing to DNS replies (tested). The event's `device_mac` is the device's MAC and `device` its name (label, DHCP hostname, or "<vendor> device"), both from `DeviceMap`'s in-memory snapshot; a client with no MAC yet is `ip:<client IP>` with the IP as its name. A new label reaches the feed at the next ARP read (at most 30 s). `scripts/fake_traffic.py` is unchanged and posts the same format, so it stays the replay fallback; run one sender at a time or the feed mixes both.

`eddie/decision.py` applies README "Decision order" from in-memory snapshots only (no disk, model or network on the hot path; median about 4 µs a lookup on the development Mac with 150k blocklist entries and 1,000 rules). Writers replace whole snapshots: `set_lists` (called once at DNS startup with `eddie/lists.py`), `set_rules` and `load_from_store` (rules and `ai_verdicts` from `eddie.db`). List entries cover their subdomains; a rule pattern `a.com` is exact and `*.a.com` covers a.com and its subdomains, with the most specific rule winning, then the newest. The short keywords `ads` and `log`/`logs` must be a whole word in a label so `uploads`, `blog` and `login` aren't blocked. Unknown domains are flagged and forwarded; one the device looks up on a regular timer is flagged with source `heuristic` and a "looked up every N s, likely telemetry" reason instead (see "Beacon and idle detection" below). A cached AI verdict never blocks on its own: `needed` allows, `tracker` flags with the reason `likely tracker: …`, `unsure` flags. On real traffic from the development Mac, `llama3.2:3b` labelled `www.gstatic.com`, Google image thumbnails, Apple's update catalog, Safe Browsing and `one.one.one.one` trackers at 0.8–0.9 confidence, so confidence doesn't separate good verdicts from bad ones. Blocking an AI-flagged domain takes a user rule: "block it", or a yes to Eddie's question about it (#79, "Ask before blocking" below). The DNS server's `StoreWatcher` checks `eddie.db` every 0.2 s in a worker thread (a cheap count and max-timestamp query on `rules` and `ai_verdicts`, plus the `rules_rev` counter) and calls `load_from_store` only when one changed, so rules and verdicts written by other processes take effect within about 0.2 s. After each reload it writes the rules revision it loaded to `engine_state.rules_loaded`.

Away mode (#109, `eddie/away.py`): `POST /mode {"away": true}` ranks devices from the last week of the query log in a worker thread on a read-only connection (interim occupancy leak score: hours with media lookups or 3× bursts; security devices exempt), stores them in `away_devices` with `away`, `away_until` and `away_rev` in `engine_state`, and waits for `away_loaded`. The watcher also checks `away_rev`; `load_from_store` hands the engine a frozen `Away(devices, until)` snapshot, and the engine checks the end time per lookup, so expiry needs no reload. For covered devices only, after the keyword step, labelled telemetry domains, AI tracker verdicts and beacons are blocked with source `away_mode`. The covered set is fixed when away turns on; a device that appears later isn't added. Tested end to end against a real DNS server (`tests/test_away.py`); not yet run on the household's real traffic, so how many devices the interim score covers there is unverified.

Sensitivity modes (#110, `eddie/sensitivity.py`): `POST /sensitivity` stores `sensitive_<mode>` and `sensitivity_rev` in `engine_state` and waits for `sensitivity_loaded`. `load_from_store` calls `Engine.set_sensitivity`, which builds a first-party-domain → mode map and one tracker set from `labels.DOMAINS` and `labels.BROKERS`, and drops open windows of modes now off. On the hot path, a lookup of a protected site records `(until, mode)` for the device in a bounded `OrderedDict` before rules are checked, so an allowed site still opens the window; after the away-mode telemetry step, a tracker or AI tracker verdict inside the window is blocked with source `sensitivity`. No model, disk or network is touched. Tested end to end against a real DNS server (`tests/test_sensitivity.py`); not yet run on real browsing, where a tracker that loads before the site's own name is looked up is missed.

Offline mode (#26, `eddie/offline.py`): the watcher also checks `engine_state.offline_rev`, switches `dns_server.offline_mode.on` to the stored `offline` value, and writes `offline_loaded`, which `POST /offline-mode` waits for. While online, every upstream answer except SERVFAIL is kept as raw bytes in an in-memory cache keyed by name, type and class (4,096 answers, oldest dropped). While offline, `resolve` never calls `forward`: allowed lookups get the cached answer with the request's ID and question and TTLs aged (30 s once expired, nothing past 24 h), or SERVFAIL; blocked lookups are unchanged. The API, dashboard, classifier (Ollama) and voice all talk to `127.0.0.1` or IP literals, so they don't depend on upstream DNS. Tested with a fake upstream that counts packets (`tests/test_offline.py`); not yet checked on hardware with the uplink actually unplugged. Offline mode stops Eddie's DNS forwarding only: in router mode it doesn't stop packet forwarding, so a device using hard-coded IPs or its own DNS (DoH) still reaches the internet.

`eddie/devices.py` (#14) keeps the IP → MAC map for DNS. The lookup only reads an in-memory dict. A background task checks every second and reads the ARP table (`ip neigh show` on Linux, `arp -an` on macOS, 2 s timeout) in a worker thread when a client IP has no MAC or hasn't been recorded yet, and otherwise every 30 s. Each read upserts the devices that looked something up since the last read into `devices` (ip, vendor, DHCP hostname, first and last seen; never the label). An IP ARP can't resolve triggers one read, not one per lookup. Vendors come from `eddie/data/oui_vendors.json`, built at setup by `scripts/build_oui.py`. `GET /devices` joins `devices` with per-device counts from `queries`; `PUT /devices/{mac}` writes the label. If ARP can't be read, every device stays keyed by IP and DNS is unaffected.

New device alert and quarantine (#98, `eddie/quarantine.py`): each MAC a read writes is checked against `device_status`. The first read on an empty table approves every known device silently; afterwards a new MAC is stored `pending` and `refresh` returns a `new_device` alert, which `watch_devices` posts to the API's `POST /devices/new` from a worker thread (`FeedPublisher.send_new_devices`). Quarantine (opt-in) and approve / deny decisions bump `quarantine_rev`; the StoreWatcher reloads the blocked set (denied, plus pending while quarantine is on) into `decision.Engine.quarantined` and writes `quarantine_loaded`, which the API waits for. The engine checks it first: a held device gets only the essentials allowlist, `source: "quarantine"`. It's DNS-only, so hard-coded IPs and DoH get past it until router mode (#22/#23); a new device's first second of lookups (before ARP and the reload) is answered normally. Tested in `tests/test_quarantine.py` with a fake ARP table; not yet checked with a real device joining the hotspot.

`eddie/rules.py` and the API's `/rules` endpoints (#12) are the rule writers. Each add or delete stores the row and bumps `engine_state.rules_rev` in one transaction, then the API waits up to 2 s for `rules_loaded` to reach that revision and returns `applied: true` only if it did. That is the DNS engine's acknowledgment, not just a stored row: once `applied` is true the very next lookup Eddie answers uses the change, and Eddie keeps no decision cache. Devices still cache earlier answers for their TTL (60 s for blocks, upstream's TTL for allowed answers), so a device may not ask again straight away. `applied: false` means the rule is stored but no running DNS server loaded it in time (DNS stopped, `EDDIE_DB` pointing at another file, or the API in Docker on a Mac while DNS runs on the host: the container has its own `eddie.db`). Voice must say so rather than claim the block worked. Each stored add or delete is also broadcast on `/ws/events` as `rule_change` (#7), before the wait, so it reports the stored row and never enforcement. The event and `GET /rules` carry the device's display name; the dashboard shows each change as a feed row and toast and lists active rules through `serve.py`'s read-only `GET /api/rules` relay (#19).

Spoof rules (#99): `decision.py` passes a rule's `spoof` action through like `allow` and `block`. `resolve` answers it with `EDDIE_SPOOF_IP` for A (TTL 60) and an empty answer for every other type, so IPv6-capable clients fall back to the A. If `EDDIE_SPOOF_IP` is unset, the spoof is answered as a block. `eddie/spoof_server.py` is a separate asyncio process (port 80, `EDDIE_SPOOF_PORT`) that reads a request head of up to 16 KB, drains and drops up to 1 MB of body, and answers `200 OK` with `Content-Length: 0`. It doesn't do TLS. The dashboard turns the house icon into Pinocchio while `GET /rules` holds any spoof rule; that is stored rules, not proof the stub server is running. Tested: decision path, DNS answers with and without the IP, rule validation, stub responses (GET, drained POST, oversized head, hang-ups) and that the stub logs nothing per request. Not tested on the Pi with a real device.

`eddie/lists.py` reads every `blocklists/*.txt` (hosts format or one domain per line; comments, IPs and hosts-file names such as `localhost` and `broadcasthost` are skipped) and `allowlist.txt`. A missing allowlist stops startup. The allowlist is kept narrow (exact hosts or single-purpose zones such as `nflxvideo.net`, never `amazon.com`), and a test fails if any allowlist entry would unblock a domain on the shipped blocklists. That's why the Prime Video zones `aiv-delivery.net` and `pv-cdn.net` aren't on it: StevenBlack blocks one host in each. The same rule keeps the Google shared-infrastructure entries host by host (`www.gstatic.com`, `encrypted-tbn0..3.gstatic.com`, `lh3.googleusercontent.com`): StevenBlack blocks `csi.gstatic.com` and some `googleusercontent.com` ad hosts. `blocklists/eddie-extra.txt` is Eddie's own short list of measurement-only hosts seen on real traffic that no shipped list blocks (GitHub's `collector.github.com`, Notion's Splunk intake, Google's `adtrafficquality.google`, ChatGPT's A/B-testing host, Cloudflare error reports). PerimeterX bot detection (`protechts.net`, `px-cloud.net`) is deliberately not on it: blocking it can make sites challenge or refuse the user. Lists change only on restart.

`eddie/classifier.py` runs separately from DNS and no longer uses Ollama (#181). `eddie/domain_model.py` is a logistic regression over the hostname's subdomain labels and words, the registered domain and its words, character 3–5-grams of both, and a few shape features (label count, length, digits). `scripts/build_domain_model.py` trains it with scikit-learn on the developer's machine; the Pi only loads the weights (`eddie/data/domain_model.json`, about 39,000 weights, 640 KB) and scores in pure Python in well under a millisecond. Labels: every host on `blocklists/*.txt` and every Cisco Umbrella top-1M hostname a blocklist covers is `tracker`; every other Umbrella hostname and the allowlist is `needed` (977,158 hosts, 100,695 listed). Hosts are split 80/10/10 by registered domain, so evaluation only sees companies the model never saw, which is what reaches the classifier. On held-out Umbrella hostnames (79,183, of which 1,386 listed) it answers `needed` for 55% at 99.65% precision against the list labels, `unsure` for 45%, and `tracker` for 0.35%. Measured against the list labels that `tracker` precision is only 28%, but the labels undercount: many unlisted hosts are trackers (Quantcast, Hotjar, Adobe `smetrics.*`, ad exchanges). A hand audit of 60 random unlisted held-out hosts the model called trackers found about 32 of the 36 that weren't from one scanner-like domain (`sussybaka.store`, 705 templated subdomains such as `metrics-01.`) to be ad or analytics hosts; the misses were a live-shopping widget, a log-analyzer demo and an ambiguous `tracking.adp.com`. The same audit set the tracker threshold (0.6) and the rule that a bare site name (no subdomain, or `www`) is never a tracker: those calls were mostly shops on suffixes that the blocklists' scam domains share. Hosts with the decision engine's tracker keywords (`metrics`, `telemetry`, `ads`, …) are blocked before they're queued, so the model mostly judges names without them; on 13 made-up such names it called 4 trackers (`adserver.`, `adnet.`, `adsync.`, `counter.`), left the rest, including generic ones such as `events.`, `collector.` and `click.`, unsure, and called none needed. A `tracker` reason names only words from the host. It judges the name alone: an unlisted tracker on a plain API-style name stays `unsure`, and the audit is one person's labelling of a small sample. The tests (`tests/test_domain_model.py`) check that 54 well-known Google, Apple and infrastructure hosts are never trackers (39 come out `needed`, 15 `unsure`) and that the golden tracker names are never `needed`. Flagged query rows are its durable queue. Network plumbing (`decision.is_plumbing`: reverse lookups, service discovery, `.local`) is never queued. The production loop scores at most two domains concurrently on a small thread pool, oldest observed first, and polls futures every 250 ms. No model is called by DNS. Inputs are domain, optional friendly device label, ten-minute lookup count and idle (no allowed, labelled media traffic in five minutes; unknown without media history). Strict validated JSON is cached in `ai_verdicts`, then DNS's watcher reloads it. Invalid output backs off for five minutes; unavailable inference backs off for ten seconds. A bounded in-memory event outbox retries local API delivery without rerunning inference. Restart can lose undelivered events, but cached verdicts remain authoritative. The initial #27 implementation is retained through its synchronous compatibility interface and tests.

`eddie/store.py` owns `eddie.db` (path from `EDDIE_DB`) and creates the README schema on first open (WAL mode, so readers don't block the writer). Every parsed DNS question writes one `queries` row with only ts (ms, arrival), device (MAC from `devices.py`, or the client IP if unknown), domain, qtype, action, source and reason; SERVFAILs are logged with the decision that was made, and non-DNS or question-less packets are not logged. The DNS task only puts the row on a bounded in-memory queue (10,000 rows); one writer thread batches inserts. If the writer falls behind, rows are dropped and counted rather than slowing DNS. Ctrl-C and SIGTERM flush the queue before exit; a hard kill loses at most the unflushed rows. Privacy measures: rows older than `EDDIE_RETENTION_DAYS` (default 7) are pruned at start and hourly with `secure_delete` plus a WAL truncate; in the same pass `store.forget` (#111) turns health, beliefs and kids lookups (`labels.SENSITIVE`) older than 24 hours into per-day, per-device counts in `sensitive_summaries` and deletes them, with their `ai_verdicts` and `baseline_domains` rows; the database files are `0600`; `EDDIE_DB=off` disables the log. The API reads it for `/devices` counts and recent blocked domains and for the live "what they know" report (`GET /what-they-know` opens its own read-only connection in the thread pool and loads the window's rows, falling back to the in-memory feed when the log has none); the live feed is still the API's own in-memory list, which drops events older than `EDDIE_RETENTION_DAYS` on every ingest and read (#129), and sensitive events older than 24 hours in a sweep at most once a minute (#111). Encryption at rest is a filesystem-level setup step on the Pi (a LUKS volume holding `EDDIE_DB`), not code; see PRIVACY.md. Every privacy decision and known gap is tracked in [PRIVACY.md](PRIVACY.md).

## Traffic monitor (#136)

`eddie/traffic.py` is an optional, separate process (`python -m eddie.traffic`); the DNS server never imports it, so DNS never waits on it. It is off until started with `EDDIE_TRAFFIC_IFACE` (or `--iface`), and refuses to start with `EDDIE_DB=off`. Live capture opens a Linux `AF_PACKET` raw socket on the LAN interface (root or `CAP_NET_RAW`) and reads at most 128 bytes of each frame, enough for Ethernet, 802.1Q, IPv4 / IPv6 and TCP / UDP headers; there is no scapy dependency. `--pcap FILE` replays a classic Ethernet pcap instead (any OS).

Direction comes from Eddie's own MAC on that interface (`/sys/class/net/<iface>/address`, or `--router-mac`): a frame to it is a device's upload, a frame from it a download. The device is the other MAC; the remote is the far IP and port, and only global addresses count, so Eddie's own DNS replies and device-to-device traffic are skipped. Without the router MAC (pcap replay) it falls back to "one side local, the other global", which misses IPv6 devices with global addresses. Bytes are the IP header's length field (headers plus payload as sent). Later IPv4 fragments and IPv6 extension headers are counted with port 0.

Counts stay in memory (at most 10,000 flows; new flows past that are dropped and counted) and are written to `traffic` every 60 s and on exit (Ctrl-C, SIGTERM), then pruned with the query log (`store.prune`, by `last_ts`). Tested against a hand-built fixture capture (`tests/fixtures/traffic.pcap`, checked with `tcpdump -r`) in `tests/test_traffic.py`.

Limits: it only sees other devices' packets when Eddie is their router (#22, not built yet). On the hotspot setup devices send packets straight to the iPhone, so the monitor sees only Eddie's own traffic and records nothing useful; Wi-Fi monitor mode isn't used. Live capture has not been run on the Pi yet. Nothing reads `traffic` yet: mic watch, camera watch and bypass detection are the planned consumers, and there is no API endpoint. nftables counters (kernel-side, no per-packet Python) are the alternative if per-packet parsing proves too slow on the Pi.

```bash
sudo EDDIE_TRAFFIC_IFACE=wlan0 .venv/bin/python -m eddie.traffic            # Pi in router mode
uv run python -m eddie.traffic --pcap capture.pcap --router-mac 02:ed:d1:e0:00:01  # replay, any OS
```

## Dashboard bridge control (#40)

`frontend/serve.py` serves the page, the `/events` SSE stream and read-only GET endpoints such as `/api/voice/status` to anyone who can reach it; with `--host 0.0.0.0` that includes the iPad. Control routes are POSTs and pass three checks in order:

1. **Host.** The `Host` header must be an IP literal, `localhost` or a `.local` mDNS name, so a DNS-rebound domain can't reach loopback controls from a browser. Then the existing same-origin check rejects cross-origin browser requests.
2. **Loopback is trusted.** Requests from the Eddie computer itself need no token.
3. **Other devices need the pairing token and only reach `/api/voice/ask`, the mode toggles (`/api/mode`, `/api/offline-mode`, #35, `/api/quarantine`, #98) device approval (`/api/devices/decide`), naming and child / adult (`/api/devices/update`) and kid mode (`/api/kid-mode`, #119). Guest Mode (`/api/guest`, #163) stays on the Eddie computer.** The token comes from `EDDIE_DASHBOARD_TOKEN`, or is random (`secrets.token_urlsafe`) on each start. When bound beyond loopback, `serve.py` prints `http://<LAN IP>:5173/#pair=<token>`. The page sends it as `Authorization: Bearer <token>` (constant-time compare). A missing or wrong token gets 401. `/api/voice/start`, `/api/voice/stop`, `/api/voice/dismiss` and `/api/events` answer 403 from any other device, with or without the token: the microphone is never switched on from the network, and traffic events only come from this machine. A paired device's typed ask of “stop recording” does turn it off, the same as saying it (#128).

The token is in the URL fragment, which browsers don't send, so it isn't in request lines or access logs, and the page keeps it nowhere but the URL. A random token changes on restart, so set `EDDIE_DASHBOARD_TOKEN` for a Home Screen link that survives restarts. There is no typed-ask box in the page yet; `window.eddie.ask(text)` is the client hook. The traffic API on port 8000 is separate: its writes need `EDDIE_API_TOKEN` from anywhere but loopback and its WebSocket checks `Origin` (#96, docs/EVENTS.md), but its reads are open.

The mode toggles (#35) relay one boolean to `POST /mode` or `POST /offline-mode` and return the API's own answer; the page shows a toggle's new state only from that answer or from the API's `mode` / `offline_mode` broadcasts, and offline mode's `applied: false` as "not yet applied by DNS". Home mode's note (#20) says "home mode on/off not yet applied by DNS" in red until `home_applied` is true, then whether it's blocking camera uploads because a household phone is home or because it was turned on by hand (or "off by hand, phones ignored"). Away mode has no toggle; the page shows a note only from `GET /mode` or the `away_mode` broadcast with `away_applied: true` (covered devices and the security devices that stay up), "not yet applied by DNS" in red otherwise, and drops the note at `away_until`. The quarantine toggle works like offline mode and always says it is DNS-only (hard-coded IPs get past it; router mode #22/#23 stops that). New and denied devices are listed first in the device list (the `devices` link) with approve / deny buttons that ask with `confirm()` before posting `/api/devices/decide`, and a `new_device` event shows a notice and a feed line.

## Beacon and idle detection (#24)

`eddie/beacons.py` holds the timing evidence. `Beacons` keeps the last 12 lookup times for each device and domain (at most 10,000 pairs, least recently seen dropped); lookups within 2 s of the previous one, such as an A and AAAA pair, count once. With at least 5 gaps, a mean gap between 10 s and 1 h and a gap coefficient of variation of at most 0.15, the pair is a beacon at that mean interval. `Idle` keeps each device's latest allowed media lookup (`labels.HUMAN`); a lookup is idle when that was 5 minutes or more before it, and unknown (`null`) if the device has had none.

- Decision engine: only lookups that reach the unknown step are timed, so listed, ruled and classified domains cost nothing extra. A beaconing unknown is flagged with source `heuristic`, and the classifier's queue takes flagged `heuristic` rows as well as `default` ones. The DNS server passes each lookup's arrival time.
- Events: the API runs its own `Beacons` and `Idle` over `/ingest` events, keyed by `device_mac`, and adds `beacon_s` and `idle` to each event (docs/EVENTS.md). This covers blocklisted and allowed domains too.
- "What they know": `inferences.beacon_fact` replays the window through a fresh `Beacons` and reports the device and domain with the most lookups made on a timer, listed or not.

Limits: devices cache answers, so a timer only shows at DNS level when the domain's TTL is shorter than the timer. A device's history restarts when its key changes from IP to MAC and when a process restarts. The thresholds are tuned on synthetic traffic and the scripted feed, not on captured Fire Stick traffic. Beacons only flag; they never block on their own.

## Self-correcting blocks (#101)

`eddie/rollback.py`'s `Watcher` lives in the API. `POST /rules` hands it each stored rule; it watches unpinned block rules other than lockdown for 10 minutes. `/ingest` runs every query event through `Watcher.observe` after broadcasting it, so this stays off the DNS hot path and needs no DNS change: a lookup is attributed to a rule by the decision reason (`device rule <pattern>` / `global rule <pattern>`) plus the device. It keeps per-device times of unblocked lookups (the baseline for a drop) and per-rule times of blocked lookups, and flags a retry storm (12 in 60 s) or a traffic collapse (other lookups at most 10% of the 10-minute pre-rule rate, at least 3 minutes after the first blocked lookup, while still retrying, from a baseline of at least 20). A hit starts `api.roll_back` as a task, so ingest never waits on DNS: it re-reads the rule (skipping one that was deleted, pinned or whose id was reused) and calls the `DELETE /rules/{id}` handler, then broadcasts `rule_rolled_back` with the delete's `applied`. `rules.pinned` (a column added to existing databases on open) and `POST /rules/{id}/pin` opt a rule out. Thresholds and the event are in [EVENTS.md](EVENTS.md#self-correcting-blocks-rule_rolled_back-101). Tested with synthetic traffic in `tests/test_rollback.py` and the dashboard event test; not checked against a real device breaking on hardware.

## Device baselines

`eddie/baselines.py` runs in the API's `/ingest`, never in DNS: after a batch's query and bypass events, `api.baseline_events` passes the batch (minus events already past retention) through `baselines.observe` in one transaction on the shared `eddie.db` connection, then broadcasts what it returned. Each event is reduced to its registrable domain (`labels.registrable_domain`, the bundled Public Suffix List). A baseline learns until both 200 lookups and one hour since its first lookup have passed, because either alone is unfair to busy laptops or quiet plugs. After that an unknown registrable domain gives one `new_domain` event and joins the baseline; more than 20 in 24 h marks the baseline `unstable` and silences it, since phones and laptops visit new sites constantly. State lives in `baselines` and `baseline_domains`; `store.prune` forgets domains and devices not seen within the retention window, so a domain unused for a week fires again; a health, beliefs or kids domain is forgotten after a day (#111). A database error skips the batch's baseline updates and logs a warning; the feed is unaffected. Events count feed events, so dropped feed events (API down, queue full) are also missing from baselines. Not built: seeding a baseline from history already in `queries`, a dashboard view, or handing new domains to the classifier. Tested in `tests/test_baselines.py` on synthetic events; thresholds aren't tuned on real household traffic yet.

## Geo alerts (#102)

`eddie/geoip.py`, run inside the DNS server. After an allowed lookup is forwarded, `resolve` hands the raw answer to `GeoWatch.observe`, which only queues it (1,000 at most, then dropped and counted), so the hot path gains one queue put; the 20 ms blocked-answer test still passes. A worker thread parses the answer with dnslib, keeps the public A and AAAA addresses (`ipaddress.is_global`, so sinkholes and LAN answers are skipped) and looks each up in `CountryDB`: DB-IP's IP to Country Lite CSV loaded into sorted range starts (IPv4 in an `array('I')`, IPv6 split into two `array('Q')`s, gaps stored as "no country") searched with `bisect`. The pinned November 2026 file (732,796 ranges) loads in about 1 s and about 15 MB on the development Mac, and a lookup takes about 5 µs; not yet measured on the Pi. `Destinations` keeps per device the countries its answers used; like device baselines it learns silently until 50 answers *and* an hour, then a new country gives one `geo_alert` to `POST /geo/alerts` through `feed.FeedPublisher.send_geo_alerts`, and more than 5 new countries in a day silences that device. State is in memory only (1,024 devices), so a restart learns again. Offline-cached answers are skipped, since they were seen when first forwarded.

Provisioning: `eddie/data/geoip.json` pins the database's URL, size and SHA-256; `scripts/provision_geoip.py` is the only code that downloads it (or copies one fetched elsewhere with `--from`; `--verify` never touches the network). The DNS server hashes the file in the worker before loading it; a missing file or a different hash logs "geo alerts off" and DNS carries on. DB-IP only keeps recent months online, so moving to a newer file means updating the pin. `EDDIE_GEOIP=off` turns it off; with `EDDIE_FEED=off` it's off too, because alerts go through the API. Country names come from `eddie/data/countries.json`, generated from tzdata's public-domain `iso3166.tab` with "the" added where English uses it.

Limits: IP geolocation is approximate. Anycast and CDN addresses are registered in one country and served from many (the pinned file puts `1.1.1.1` in Australia), so alerts say "started talking to a server in", never where data ended up, and every one carries that caveat. A device whose MAC isn't known yet is keyed by `ip:<IP>` and learns again once ARP names it. Only DNS answers are seen: a device using hard-coded IPs or its own resolver (see Bypass detection) never shows up. Tested with a fixture database and synthetic answers (`tests/test_geoip.py`), and smoke-tested against the real pinned file; not yet run on household traffic or the Pi.

## ACR blocker (#104)

`eddie/acr.py` holds `ACR`, smart-TV automatic content recognition domains with their provider and source for each (Anis et al., IMC 2024, for Samsung and LG; the bundled Perflyst smart-TV list; FTC v. Vizio for Inscape); an entry covers its subdomains. Eddie never sees what an ACR request carries, so a seeded domain counts as ACR only once the device looks it up on a regular timer (`beacons.py`, at least 6 lookups).

- Decision engine: after the blocklist step, an ACR domain is timed with the engine's `Beacons`; once it beacons it's blocked with source `heuristic`, and `Engine.acr_caught` (at most 10,000 device and domain pairs, memory only) keeps it blocked for that device until restart, so a TV that retries faster after the block can't unblock itself by breaking its timer. Rules and the allowlist still win; a blocklisted ACR domain keeps source `blocklist`.
- Events: the API's `/ingest` runs each query event through `acr.Sightings` after the bypass check and pushes `acr_detected` when the event is a DNS-server block and the API's own timing gave it a `beacon_s`, once per device and domain an hour. `interval_s` is that measured `beacon_s`; no timer, no event, and an allowed or flagged lookup never produces one, so the card's "Blocked." always comes from the DNS decision.
- Dashboard: an `[acr blocked]` feed row, a toast and an "acr blocked" card listing the latest detection per device and domain (up to 3 shown).

Limits: the seed list is short and from published sources, not from a TV on this network, so other makers' ACR (Roku, TCL, Hisense, Sony) isn't covered unless its domain is added. Devices cache answers, so a timer only shows when the domain's TTL is shorter than the ACR interval. Tested on synthetic beacon traffic in `tests/test_acr.py` (through the decision engine and `/ingest`) and the dashboard event test.

## Privacy settings coach (#112)

`eddie/coach.py` holds `GUIDES`, one hand-written guide per device type (Fire TV and Ring so far): where the settings live, each step with what it does, a note, a one-sentence spoken version, and the maker's help pages it came from. `coach.kind` recognises a device from its label or DHCP hostname first ("Fire Stick", "Front Door Ring"), then its MAC vendor (`Ring`) or a lookup only that kind makes (`ring.com`, `firetvcaptiveportal.com`), and an Amazon vendor with "TV" in its name. `GET /suggestions` runs that over the devices table and the last week of the query log on a read-only connection in a worker thread, and answers with each recognised device, its guide and a spoken `text`; nothing is stored. Voice routes "how can I improve my privacy", "privacy tips", "any suggestions", "make my Fire Stick more private" and "what settings should I change" to it deterministically and speaks `text`; the local model isn't involved. The dashboard's **suggestions** button opens a panel with the steps and source links.

Eddie never signs in to a device account or changes a setting: there is no write path, and the reply says so. Limits: two device types; an Amazon device that isn't named and never looks up the Fire TV captive-portal check isn't recognised as a Fire TV; the guides are copied from the makers' pages as of 2026-11-07 and go stale when the menus change. Tested in `tests/test_coach.py` (lookup, endpoint, voice routing); not yet checked against a real Fire TV or Ring account.

## Bypass detection (#97)

`eddie/bypass.py` holds `RESOLVERS`, encrypted DNS resolver names (DoH, DoT and Android Private DNS) seeded from the curl wiki's public resolver list, Chromium's DoH provider table and Firefox's default providers; an entry covers its subdomains. The API's `/ingest` runs each query event through `bypass.Suspicions` after broadcasting it and pushes `bypass_suspected` (device, name, provider, `blocked`) once per device and name every 10 minutes, so detection stays off the DNS hot path. `EDDIE_BLOCK_DOH=on` sets `decision.engine.block_doh` at DNS startup, which blocks those names after the blocklist step; rules and the allowlist still win. Blocking a name only stops clients that set their resolver up by name; one that has the resolver's IP still skips Eddie, and nothing here detects that. Not built: flagging a device that goes quiet on DNS while clearly active (Eddie only sees DNS, so it can't yet tell "active"), and DoT on port 853 to hard-coded IPs (needs router mode). Tested in `tests/test_bypass.py` and the dashboard event test; not yet checked against a real Android Private DNS or browser DoH setting on hardware.
