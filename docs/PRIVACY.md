# Eddie privacy decisions (demo build)

Eddie watches a household's network, so Eddie itself holds the most sensitive data in the house: which device talked to which company, and when. This page records every privacy decision made for the hackathon demo. Each one is marked **implemented** (in code, tested where noted), **planned** (in the README or a ticket, not built), or **gap** (a known way we fall short today). Keep it current when any of these change.

**Principle:** Eddie sees where data goes, not what's inside it. Everything is processed on the box. Nothing about the household is sent anywhere, except what's listed under [What leaves the house](#what-leaves-the-house).

## Query log database (`eddie.db`)

Owner: [eddie/store.py](../eddie/store.py), written by [eddie/dns_server.py](../eddie/dns_server.py). Tests: [tests/test_store.py](../tests/test_store.py) and [tests/test_dns_server.py](../tests/test_dns_server.py).

| Decision | Status |
| --- | --- |
| History is stored on disk on the box, never in the cloud. The weekly report, per-device grades and undo all need it. | implemented |
| Each `queries` row holds only time (ms), device, domain, qtype, action, source and reason. No DNS answers, resolved IPs, packet bytes, URLs or page content. Schema is checked by a test. | implemented |
| **Retention:** rows older than `EDDIE_RETENTION_DAYS` (default **7**) are deleted when the server starts and every hour, including while the network is idle. Seven days is the weekly report's window and no longer. | implemented |
| **Deleted means deleted:** `PRAGMA secure_delete=ON` zeroes pruned rows' bytes, and the WAL is checkpointed and truncated after a prune so old pages don't linger there. | implemented |
| **Owner-only file:** `eddie.db`, `-wal` and `-shm` are mode `0600`; an existing looser file is tightened on start. | implemented |
| **Off switch:** `EDDIE_DB=off` logs nothing and creates no file. DNS filtering still works. | implemented |
| Logging never slows DNS. Rows go on a bounded in-memory queue (10,000), and a writer thread inserts them. If the disk stalls, rows are dropped and counted, never waited on. | implemented |
| `eddie.db*` is git- and docker-ignored. | implemented |
| The device column holds the device's MAC, or its client IP when ARP can't resolve it. A phone's private Wi-Fi address changes per network (and can rotate), so one phone can show up as several devices. | implemented |
| **Encryption at rest (#129): filesystem-level, not SQLCipher.** On the Pi, `EDDIE_DB` points into a LUKS-encrypted volume (a partition or loop file mounted at `/var/lib/eddie`), so the database, `-wal` and `-shm` are all covered with no code change. SQLCipher was rejected: it replaces the stdlib `sqlite3` everywhere (store, API, devices, rules, classifier) with a native build that has to be compiled for both the Mac and the Pi, and it still needs its key on the box. See [Encrypting `eddie.db` at rest](#encrypting-eddiedb-at-rest). | planned: setup step, not yet done or verified on the Pi |
| Until that volume is set up, the file is not encrypted at rest. Anyone with root, or the SD card, can read up to 7 days of history. Even once it is, encryption only protects a powered-off or stolen card: root on the running box reads the mounted volume, and a key file stored on the same card protects nothing. | gap |
| A hard kill (`kill -9`, power loss) loses queued rows. That's safe for privacy but leaves a hole in the history. Ctrl-C and SIGTERM flush first. | known behaviour |
| **Forget timer (#111, `store.forget`):** lookups of health, kids and beliefs domains (the `labels.py` categories `health`, `kids`, `news`, `religion` and `politics`, listed in `labels.SENSITIVE`) are kept raw for 24 hours only. The same hourly pass that enforces retention (and the one at start) counts each older row into `sensitive_summaries`, one row per local day, device MAC and group (health, beliefs or kids) holding only a lookup count, then deletes the `queries` rows with `secure_delete` and truncates the WAL. No domain, company or time finer than the day survives. `ai_verdicts` and `baseline_domains` rows for those domains go after 24 hours too, so a device that uses a health site every few days raises `new_domain` again each time. Summaries are deleted once their day is past `EDDIE_RETENTION_DAYS`. Nothing reads them yet. The category comes from the hand-written table at the time of the pass, so a sensitive site that isn't in the table is kept for the full retention like any other lookup. The live feed drops these events after 24 hours too (below). Up to an hour late, as with retention. Tested in [tests/test_forget_timer.py](../tests/test_forget_timer.py), including that a deleted domain's bytes aren't left in the database file. | implemented |
| **Devices** (`eddie/devices.py`, #14): the `devices` table holds MAC, current IP, vendor, DHCP hostname, the user's label, whether the user marked it as a child's (`kid`, #119) or a household phone (`phone`, #20), and first / last seen. Only devices that looked something up through Eddie are recorded, never every ARP neighbour. Unlabeled devices not seen for `EDDIE_RETENTION_DAYS` are deleted with the query log; labeled devices and devices marked as a child's or a household phone are user settings and kept, like rules. The kid and phone flags are only a yes/no the user sets; Eddie never guesses a device is a child's or a phone from its traffic. With `EDDIE_DB=off` nothing is recorded (the IP → MAC map stays in memory for rules). Tested. | implemented |
| Device identification makes no network requests: the ARP table is read from the local kernel, vendor names come from a bundled table (`eddie/data/oui_vendors.json`), and hostnames only from a local DHCP leases file. No reverse DNS, which would send the household's private IPs to an upstream resolver. | implemented |
| `rules` holds only pattern, action, device (MAC, or client IP), scope, who created it, when, and whether it is pinned (#101). A deleted rule is deleted, not kept as history. Rules are user settings, so they are not pruned by `EDDIE_RETENTION_DAYS`. `engine_state` holds the rules revision written and loaded, offline mode's state and revisions written and loaded (#26), away mode's state and end time (#109), quarantine's state (#98), home mode's state and whether it was set by hand (#20), sensitivity modes (#110), spoof mode's on/off state, and each mode's written/loaded revisions; it stores no spoofed request bodies. | implemented |
| **New device status** (#98, `eddie/quarantine.py`): `device_status` holds MAC, approved / pending / denied, when it was first recorded and when it was decided. Approved and denied rows are user settings and kept like labels, so the table is a lasting list of every MAC the household decided about; a pending row is deleted once its `devices` row is pruned. A `new_device` alert (MAC, name, IP, vendor, DHCP hostname, time) goes only to the local API, is pushed to `/ws/events` clients and isn't stored or logged by the API. Tested. | implemented |
| **Traffic monitor** (#136, `eddie/traffic.py`): optional and off unless started with `EDDIE_TRAFFIC_IFACE`, as its own process. It reads only packet headers (at most 128 bytes a frame) and stores, per device MAC, remote IP, remote port and protocol: first and last seen (ms), and bytes and packets each way, one `traffic` row per flow per minute. No payloads, URLs, SNI, DNS answers or local IPs are kept or logged; a test checks payload bytes never reach `eddie.db`. Device-to-device LAN traffic isn't recorded. Counts wait in memory (at most 10,000 flows) and rows are pruned with the query log after `EDDIE_RETENTION_DAYS`. With `EDDIE_DB=off` it refuses to start. Remote IPs still reveal which services a device talks to, like domains do. Nothing reads the table yet and no API exposes it. Tested with a hand-built fixture capture. | implemented |
| `ai_verdicts` holds one row per domain (label, confidence, reason, time): no device or IP. A tracker verdict from behavior (#204) carries counts in its reason ("Looked up 6 times in an hour, 4 while idle", or the timer interval), never which device. To judge that, the classifier reads one device's lookup times and media lookups for that domain from the last hour of `queries`, in memory only. It is pruned with the query log after `EDDIE_RETENTION_DAYS`, because the list of domains a household looked up is history even without times. A domain seen again is classified again. Tested. | implemented |
| **Offline mode's answer cache** (#26, `eddie/offline.py`): the DNS server keeps the last upstream answer per name and type (resolved IPs included) in memory only, at most 4,096 and served for at most 24 h, so offline mode can still answer. Nothing is written to `eddie.db` or disk, it isn't exposed by the API, and a restart clears it. It's kept even with `EDDIE_DB=off`, where offline mode can't be switched on. Tested. | implemented |
| **Away mode** (#109, `eddie/away.py`): turning it on reads the last week of `queries` read-only to score devices, and stores only each covered or exempt device's key (MAC or client IP) and score in `away_devices`, plus the on/off state and end time in `engine_state`. Turning it off deletes every `away_devices` row. `POST /mode` and the `away_mode` broadcast return those keys, display names and scores to anyone who can reach the API (see the API's authentication gap below). A leak score is itself a measure of when a device is used, so it is kept no longer than away mode is on. Away mode isn't relayed by the dashboard bridge, so a paired device can't set it. Tested. | implemented |
| **Sensitivity modes** (#110, `eddie/sensitivity.py`): `engine_state` keeps only which of health, kids, money and beliefs are on. To block trackers around a protected site, the DNS server holds in memory, per device, which mode's site it last looked up and when that window ends, 5 minutes on (at most 10,000 devices; never written to disk, gone on restart or when the mode is turned off; the site itself isn't kept). The blocks it makes are ordinary `queries` rows (source `sensitivity`), kept and pruned like every other lookup. Their reason never names the site, but it does name the mode ("health protection: …"), and the forget timer (#111) only summarises lookups of health, beliefs and kids domains, so a tracker row saying a health site was opened within the last 5 minutes stays until normal retention prunes it. `POST /sensitivity`, `GET /sensitivity` and the `sensitivity` broadcast say which modes are on to anyone who can reach the API. Tested. | implemented / gap |
| **Device baselines** (`eddie/baselines.py`): the API stores, per device key (MAC or client IP), the baseline's state, when learning started and ended, a lookup count while learning and last seen (`baselines`), and each registrable domain the device looked up with first and last seen and whether it was learned in the window (`baseline_domains`). No full names, times of each lookup or actions. This is a per-device list of the sites it uses, so it is history: domains not looked up for `EDDIE_RETENTION_DAYS` and baselines of devices not seen for that long are deleted with the query log (last seen is updated at most hourly, so up to an hour late). `DELETE /devices/{key}/baseline` deletes one device's rows at once. `new_domain` events and `GET /baselines` / `GET /devices/{key}/baseline` (up to 20 recent new domains per device) are readable by anyone who can read the API, like the feed. With `EDDIE_DB=off` nothing is stored. Fake traffic posted to `/ingest` builds baselines for its invented devices too; reset them. Tested. | implemented |
| **Geo alerts** (#102, `eddie/geoip.py`): the DNS server reads the resolved addresses in forwarded answers in a worker thread and looks them up in a local file; it keeps, in memory only, per device key (MAC or `ip:<IP>`, at most 1,024) the countries its answers used with when each was first seen, an answer count and its first time. No addresses, domains or answers are kept after the lookup, nothing is written to `eddie.db` or disk, and a restart clears it. A `geo_alert` (device key and name, domain, one IP, country, the device's earlier countries) goes only to the local API, which keeps the last 50 in memory for the snapshot and pushes them to `/ws/events`; it isn't logged. The country list is itself a coarse history of where a device's services are, readable by anyone who can read the API. The lookup makes no network requests; the database is fetched only by `scripts/provision_geoip.py` at setup and refused at runtime unless its SHA-256 matches the pin. `EDDIE_GEOIP=off` turns it off. Tested. | implemented |
| **No new store for the classifier's queue.** It reads the flagged rows already in `queries`, so classification keeps nothing beyond the query log, and with `EDDIE_DB=off` nothing is classified at all. | implemented |

## Traffic API and live feed (port 8000)

| Decision | Status |
| --- | --- |
| The API keeps recent events in memory only (at most 20,000), so a restart wipes them. It does not read the `queries` table. | implemented |
| **Feed retention (#129):** the feed keeps no more history than `eddie.db`. Events older than `EDDIE_RETENTION_DAYS` (default 7) are dropped on every ingest and every read (`/events`, `/summary`, `/what-they-know`'s feed fallback, the `/ws/events` snapshot), so they expire even while the network is idle. An event that arrives already older than the window is counted and broadcast but never kept. Trimming goes from the oldest arrival, so an out-of-order old event can sit behind a newer one until that one expires too. Health, beliefs and kids events (#111) are dropped from anywhere in the feed once they're 24 hours old, in a sweep that runs on a read or ingest at most once a minute, and one that arrives already older than that is never kept. Tested in [tests/test_feed_retention.py](../tests/test_feed_retention.py) and [tests/test_forget_timer.py](../tests/test_forget_timer.py). | implemented |
| The DNS server sends every lookup (time, client IP, domain, qtype, action, source, reason: the same fields as a `queries` row) to `POST /ingest` over plain HTTP ([eddie/feed.py](../eddie/feed.py)). `EDDIE_API_URL` must be `localhost` or a loopback or private IP literal; public hosts and hostnames are refused at startup, redirects aren't followed and proxy settings are ignored, so lookups can't leave the house this way. Events wait only in a bounded in-memory queue (1,000) and are dropped, not stored, when the API is unreachable. Events are never written to the DNS server's log. `EDDIE_FEED=off` sends nothing. Tested in [tests/test_feed.py](../tests/test_feed.py). | implemented |
| With `EDDIE_API_URL` set to another machine's private IP, every lookup crosses the local network unencrypted and unauthenticated, readable by anyone on that network. The default keeps it on the box. | gap |
| Docker publishes the API on `127.0.0.1` only. `EDDIE_BIND=0.0.0.0` is an explicit opt-in to reach it from the iPad. | implemented |
| **Write auth** (#96): every `POST`, `PUT` and `DELETE` (`/ingest`, `/ai/verdict`, `/mode`, `/offline-mode`, `/rules`, `/rules/{id}/pin`, `/devices/{key}`, `/quarantine`, `/devices/{mac}/approve|deny`, `/devices/new`, `/devices/{key}/baseline`) from anywhere but loopback needs `Authorization: Bearer <EDDIE_API_TOKEN>` (constant-time compare), else 401. With no token set, nothing off loopback can write. The DNS feed, classifier, voice agent, dashboard bridge and fake traffic send the token when `EDDIE_API_TOKEN` is set. In Docker even host callers aren't loopback, so `scripts/run_all.sh` makes a random token per run (unless one is set) and hands it to the containers and host processes; it is never printed or written to disk. A browser write is refused (403) unless its `Origin` is a loopback page or a page on the same IP or `.local` host the request names, so a web page or a DNS-rebound domain can't flip modes or add rules through a local browser. Tested (`tests/test_api_auth.py`). | implemented |
| Reads stay open: with `EDDIE_BIND=0.0.0.0`, anyone on the network can still `GET` the feed (`/events`, `/summary`, `/what-they-know`, `/burglars-eye`, `/baselines`, `/devices/{key}/baseline`), the rules, `/mode` (with away mode's covered devices and their leak scores, i.e. which devices are used most), and the device list (`/devices`: MACs, IPs, hostnames and per-device lookup counts), and open `/ws/events` from a non-browser client. The token travels over plain HTTP, readable by anyone sniffing the LAN, and there is no rate limit. | gap |
| `/devices` reads per-device counts from the query log, plus how many distinct domains were blocked for each device and the three latest of them (#35), and the three domains each device looked up most recently whatever the answer (#119), so the dashboard's device list can show which device is which. It writes only labels and the kid flag. The dashboard shows those recent domains to anyone who can open it, like the live feed already does; they come from the query log and go with it after `EDDIE_RETENTION_DAYS`. With `EDDIE_DB=off` it answers 503. | implemented |
| `/rules` reads and writes `eddie.db` (`EDDIE_DB`); it never reads the query log. Each stored add or delete is pushed to every `/ws/events` client as `rule_change` (pattern, action, device, who created it, when); it is not logged or kept in memory. With `EDDIE_DB=off` it answers 503 and stores nothing. In Docker the API uses a database inside the container, which is lost on rebuild and not shared with a DNS server on the host. | implemented |
| **Ask before blocking** (#79, `eddie/questions.py`): the API keeps open and waiting questions in memory only: each tracker domain, the verdict's short reason and the name of the device that looked it up last (its label, never its MAC or IP), plus the set of domains already offered (at most 5,000). Nothing new is written to `eddie.db` or disk; a restart clears it. Questions and answers (`question`, `question_resolved`) are pushed to every `/ws/events` client, like the rest of the feed; answering is a write, so off loopback it needs the API token (#96). An answer writes ordinary rules (`created_by: dashboard` or `voice`). Tested. | implemented |
| `/ws/events` checks `Origin` (#96): a browser page may connect only from loopback (`localhost`, `127.0.0.1`, `[::1]`) or from the same IP or `.local` host the socket was opened to (the dashboard on the iPad); other origins, `null`, and DNS-rebound domains are refused at the handshake. Any page served from this machine on any port still counts as Eddie's own. Tested. | implemented |
| uvicorn's default access log (request paths, client IPs) goes to Docker's container log. No request bodies are logged, so rule patterns aren't; a `DELETE /rules/{id}` path shows only the id. | known behaviour |
| The feed has no time-based retention; old events only drop out after 20,000 newer ones. | gap |
| Self-correcting blocks (#101, `eddie/rollback.py`): the API keeps, in memory only, the times (no domains) of each device's unblocked lookups over the last 20 minutes (at most 5,000 per device), and for each block rule added in the last 10 minutes (at most 200) the times of lookups it blocked per device. Nothing is written to disk; a restart clears it. A rollback deletes the rule through `DELETE /rules/{id}` and pushes `rule_rolled_back` (the rule, the device's key and name, which sign, a reason naming the blocked domain and a rate) on `/ws/events`; it is not logged. It makes no network requests. Tested with synthetic traffic. | implemented |
| Geo alerts (#102): `POST /geo/alerts` is a write, so off loopback it needs the API token; the alerts it pushes are readable like the rest of the feed. | implemented |
| Bypass detection (#97, `eddie/bypass.py`): the API checks each feed event's domain against a bundled list of encrypted DNS resolver names and pushes `bypass_suspected` (device, resolver name, whether DNS blocked it) on `/ws/events`. It keeps the last time per device and name (at most 10,000) and the last 50 events in memory only; nothing is written to `eddie.db` or disk, and a restart clears it. It makes no network requests. `EDDIE_BLOCK_DOH=on` blocks those names at DNS. It can't see DoH/DoT to hard-coded resolver IPs, so it never tells you a device is fully covered. Tested. | implemented |
| ACR blocker (#104, `eddie/acr.py`): the DNS server keeps, in memory only, each device and smart-TV content recognition domain it has caught beaconing (at most 10,000) so it stays blocked until restart. The API pushes `acr_detected` (device, domain, provider, measured interval, lookup count) on `/ws/events` and keeps the last time per device and domain (at most 10,000) and the last 20 events in memory only; nothing is written to `eddie.db` or disk, and a restart clears it. It makes no network requests. Anyone who can read the feed sees which TV was reporting what it shows and how often. Tested on synthetic traffic. | implemented |
| CNAME uncloaking: the DNS server reads the CNAME records of answers it already forwards and keeps, in memory only, the domains whose CNAME hit the blocklist (at most 10,000, gone on restart). Nothing is sent anywhere new; the query row's reason names the blocklist entry the CNAME matched. | implemented |
| Beacon and idle detection (#24, `eddie/beacons.py`) keeps only lookup times in memory: the last 12 per device and domain (at most 10,000 pairs) and each device's latest streaming lookup (at most 1,000 devices), in the DNS server for unknown domains and in the API for feed events. Nothing new is written to `eddie.db` or disk, and a restart clears it. Each feed event gains `beacon_s` and `idle`, which say when a device runs on a timer or reports while nobody is watching, and anyone who can read the feed sees them. Tested. | implemented |

## Voice (wake word, speech to text, speech)

| Decision | Status |
| --- | --- |
| All wake detection, transcription and speech run locally. There is no cloud speech fallback. | implemented |
| Models are provisioned once at setup. At runtime Whisper uses `local_files_only`, `HF_HUB_OFFLINE=1` is set, Hugging Face telemetry is off, and Piper loads a local file. | implemented |
| Audio stays in memory and is bounded: a small pre-roll, at most 10 s per command, ended by 800 ms of silence. Nothing is written to disk. | implemented |
| Transcripts and replies are never stored or logged. | implemented |
| **Replies on the dashboard (`EDDIE_SPEAKER=ipad` or `both`):** each spoken reply is also kept in memory as one WAV clip, replaced by the next reply and never written to disk, and served at `/api/voice/audio/<random id>` over plain HTTP. Like the reply text already sent on `/events`, anyone on the network who learns the id from that stream can fetch it, and it crosses the Wi-Fi unencrypted. Every open dashboard plays it, so a second screen speaks too. The default (`pi`) sends no audio. | implemented |
| **Timers and reminders** (#122, `voice/timers.py`): the one exception to the line above. Pending items are written to `EDDIE_TIMERS_FILE` (default `voice/timers.json`, mode `0600`, git- and docker-ignored): kind, due time, a timer's length and a reminder's task in the user's words (“call my mom”). An item is deleted from the file when it rings or is cancelled, so nothing is kept as history. `EDDIE_TIMERS_FILE=off` keeps them in memory only. The file isn't encrypted, and anyone who can ask Eddie (including a paired iPad, by typed ask) can hear the list read aloud. Tested. | implemented |
| **House guide** (#165, `voice/house_guide.py`): the owner's notes live in `EDDIE_HOUSE_GUIDE` (default `voice/house_guide.json`, git- and docker-ignored, plain unencrypted JSON) and are read on each question, never copied, logged or printed. Guest questions and the guide's answers are handled like any transcript and reply: not stored or logged, but shown on the dashboard and streamed over `/events` (the transcript gap below), so anything marked `guest` (a Wi-Fi password, a door code) appears there when spoken. The guide never reaches the local model. Entries are owner-only unless marked `guest`. Eddie can't tell voices apart, so owner entries are spoken to anyone who asks while Guest Mode (#163) is off; while it's on, only guest entries, and only if the owner approved the house guide for guests. A guest asking about an owner entry hears the same “ask the host” as for a missing topic. The starter example and the demo guide (`voice/house_guide.demo.json`) hold no real credentials or personal data; the demo's Wi-Fi password is made up. `GET /api/guest` also lists the guest entries' topic names (never their answers) so the dashboard can show what guests may ask; like the rest of the page, anyone who can load the dashboard sees them. Tested. | implemented |
| The mic ignores audio while Eddie speaks, so Eddie never transcribes itself. | implemented |
| The mic starts only on an explicit start request, not on page load, **except on the Pi**: its `eddie-dashboard` unit sets `EDDIE_MIC_AUTOSTART=1`, so the mic opens when the service starts (boot, restart, every auto-update) and listens for the wake word with no one pressing start, because the box has no screen. `EDDIE_MIC_AUTOSTART=0` in `/etc/eddie/eddie.env` turns that off. A spoken “stop recording” still stops it until the next start. Once on it stays on until someone says “stop recording” (or “stop listening”, “turn off the mic”), or the local model calls `stop_microphone`; that takes no yes. The dashboard has no stop button. Tested. | implemented |
| A missing custom wake model is an error, never a silent switch to another engine. | implemented |
| **Prototype wake engine (Vosk, the dev default):** the recognizer is restricted to "hey eddie", "hey eddy" and `[unk]`, so room speech is decoded only as the wake phrase or "unknown", never written out as other words; nothing is kept either way. It still hears all room audio, as any wake engine must. Before this change it transcribed all room speech in full to spot the phrase. | implemented |
| Transcripts are streamed live over the dashboard's `/events` SSE stream. Any local process can subscribe because GET has no origin check, though the text is never stored. | gap |
| Mic indicator (#128): a mic icon, first in the dashboard's heading row, shows only while the mic stream is open (status `ready`) and hides on off or error. It isn't shown inside the full-screen Eddie overlay, and there is no hardware mic switch. Tested (`tests/test_frontend_events.cjs`). | implemented |
| Offline installer with pinned hashes (#39): `scripts/provision_voice.py` is the only code that downloads voice models, from the pinned URLs in `voice/assets.json` (Hugging Face, GitHub releases, alphacephei.com). Those hosts see the setup machine's IP and which public models it fetched, nothing about the household. `--verify` and the launcher's pre-start check never use the network. The hardware check lists audio devices but opens no stream. Tested. | implemented |

## Dashboard and voice bridge (port 5173)

| Decision | Status |
| --- | --- |
| `frontend/serve.py` binds `127.0.0.1` by default; `--host 0.0.0.0` / `EDDIE_DASHBOARD_HOST` is an explicit opt-in for the iPad. | implemented |
| Cross-origin POSTs are rejected; bodies are capped at 64 KB and typed asks at 1,000 characters. | implemented |
| The page loads no external fonts, scripts, analytics or cloud audio. | implemented |
| The page keeps nothing in `localStorage`, `sessionStorage`, IndexedDB or cookies; a pending action's read-back is cleared from the screen on answer, dismissal or expiry. Tested (`tests/test_frontend_events.cjs`). | implemented |
| `GET /api/rules` relays the traffic API's rule list (pattern, action, device name and MAC or IP, who created it, when) read-only. With `--host 0.0.0.0`, anyone on the network who can open the dashboard can read the household's rules, even if the API itself stays on loopback. It cannot change them. | known behaviour |
| `GET /api/devices` and `GET /api/mode` (#35) relay the device list (names, MAC or IP, vendor, DHCP hostname, lookup counts and each device's latest blocked domains) and the mode state read-only, so with `--host 0.0.0.0` anyone on the network who can open the dashboard can see which devices are in the house and what Eddie blocked for each, even if the API stays on loopback. The page shows names, counts and blocked domains, not MACs or IPs, unless a device has no other name. Nothing is stored in the browser. | known behaviour |
| **Bridge controls** (#40): microphone start/stop and `/api/events` are refused from any device but the Eddie computer, token or not. Another device can only send a typed ask (`/api/voice/ask`), close Eddie's conversation (`/api/voice/dismiss`, which ends the conversation but leaves the mic as it was), flip home or offline mode or quarantine (`/api/mode`, `/api/offline-mode`, #35, `/api/quarantine`, #98), approve or deny a device (`/api/devices/decide`), name a device or mark it as a child's (`/api/devices/update`), switch kid mode (`/api/kid-mode`, #119), or switch Guest Mode and its approvals (`/api/guest`, #163), and only with the pairing token (`Authorization: Bearer`); otherwise 401. POSTs whose `Host` isn't an IP, `localhost` or `.local` are refused (DNS rebinding). Tested (`tests/test_dashboard_bridge.py`). | implemented |

## Encrypting `eddie.db` at rest

Decided in #129; a setup step on the Pi, not code. Nothing here has been run on the hardware yet.

1. Create a LUKS volume for Eddie's data: a spare partition, or a loop file (`cryptsetup luksFormat /var/lib/eddie.img`), and mount it at `/var/lib/eddie`.
2. Keep the key off the SD card: a passphrase typed at boot over SSH (dropbear in the initramfs), or a key file on a USB stick kept apart from the box. A key file on the card itself makes the encryption pointless, because whoever has the card has the key. The Pi has no TPM to seal it to.
3. Run the DNS server and API with `EDDIE_DB=/var/lib/eddie/eddie.db`. The `-wal` and `-shm` files sit next to it, so they are covered too, and secure delete and `0600` still apply inside the volume.
4. If the volume isn't mounted, Eddie must not quietly create a plaintext database on the card instead: the service should depend on the mount (`RequiresMountsFor=/var/lib/eddie` in systemd).

What it does not cover: root on the running box, the in-memory feed, and the development Mac (use FileVault there).

### Pi services (#18)

`scripts/install_pi.sh` writes `/etc/eddie/eddie.env`, mode `0600` and owned by root, which systemd reads for the `eddie-*` units. It holds a fixed `EDDIE_API_TOKEN` and `EDDIE_DASHBOARD_TOKEN`, so unlike `run_all.sh`'s per-run token these **are stored on disk** (unencrypted on the SD card unless the card or `/etc` is encrypted) and last until the file is edited or deleted. Anyone with root on the Pi, or the card in hand, can read them and write rules or pair a device. Rerunning the installer keeps them; delete the file and rerun it to rotate both. The services run as the installing user, and the DNS server gets only `CAP_NET_BIND_SERVICE`, not root. Their output goes to journald, which keeps what the processes already log (no raw audio or transcripts by default) under the Pi's journal settings. `run_pi.sh` keeps a per-run token in memory like `run_all.sh`. Not yet run on the hardware.

**Auto-update (`eddie-update.timer`):** every 5 minutes the Pi makes an anonymous HTTPS `git fetch` from github.com (the public `adityarvij/eddie` repo), so GitHub sees the home's public IP and that it's polling, about 288 times a day. When main has moved it also downloads packages from PyPI through uv (and voice models from the pinned `voice/assets.json` hosts if those changed). No traffic data, tokens or logs are sent; the fetch carries nothing from `eddie.db`. Code from main runs as the service user with no review on the Pi, so whoever can merge to main can run code on the box. `sudo touch /etc/eddie/hold` stops all of it, and `sudo systemctl disable --now eddie-update.timer` turns it off.

### Classifier event delivery (#27, implemented)

The worker retains at most two in-flight inference inputs and 1,000 undelivered verdict events in memory. Worker shutdown/restart drops its in-memory notification outbox. Persistent verdict retention stays unchanged. Model reasons are untrusted display text, never HTML.


## Real AI on the scripted demo feed

`python -m eddie.feed_classifier` polls the local API for scripted demo queries and feeds the real bounded classifier worker (the local domain model) using an in-memory SQLite queue/cache. Real DNS still uses the durable database worker. `run_all.sh` launches the adapter only with the fake-traffic profile. Stopping it loses its cache, and no demo network history is added to disk. It polls up to 2,000 recent events once per second and retains at most 20,000 query rows for an hour; heavy traffic can outrun that window. Inference remains on the host with local-only URLs, not in the DNS or API request path.

The API retains at most 1,000 verdicts in memory, returns them from `GET /ai/verdicts`, and includes `ai_verdicts` in WebSocket snapshots so a browser refresh does not hide completed results. The fake generator uses these real cached verdicts for later decisions, while still labelling the traffic itself as scripted demo traffic in its launcher/docs. The old hard-coded “sent to AI” and fabricated AI confidence text are removed. Unknowns say “awaiting classification”; an AI line (`[approved (ai)]`, `[unsure (ai)]` or `[flagged (ai)]`, coloured like that DNS result and stamped with the verdict time) is printed only after actual model output is validated; snapshot verdicts are shown among the DNS lines in time order. A tracker reads flagged, never blocked, because the AI does not block. These verdicts do not prove anything about real Fire Stick traffic.
